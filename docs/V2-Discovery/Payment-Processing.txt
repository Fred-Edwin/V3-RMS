## Wendo Coffee Bistro — Payment Processing Workflow (V2)

### Current State

Payment processing in V1 is handled outside the system entirely. When a customer is ready to pay, the waiter uses a Pesapal POS device to either trigger an Mpesa STK push to the customer's phone or collect a card payment. Once payment is confirmed on the device, the waiter returns to the RMS and manually marks the order as paid through the confirmation UI. The system records the payment method but plays no role in initiating or verifying the actual transaction.

This means the RMS and the payment process are two separate, disconnected workflows. The waiter has to manage both simultaneously — the system on their phone and the Pesapal device in their hand.

---

### What V2 Needs to Do

The core goal of the V2 payment module is to bring payment initiation directly into the waiter's app, eliminating the need for a separate POS device for Mpesa transactions. Instead of picking up a Pesapal device, the waiter should be able to trigger an Mpesa STK push to the customer's phone from the same interface they use to manage orders — without leaving the app or involving any external hardware.

---

### Mpesa STK Push — Waiter Flow

When a customer is ready to pay via Mpesa, the waiter opens the order in their app, enters the customer's phone number, and triggers the STK push directly from the RMS. The customer receives the Mpesa prompt on their phone, enters their PIN, and completes the payment. The system receives a confirmation callback from Mpesa and automatically marks the order as paid — without the waiter needing to manually confirm it. The waiter simply waits for the confirmation to appear in the app.

This collapses what is currently a two-device, multi-step process into a single flow on the waiter's phone.

---

### Card Payments

Card payments currently rely on Pesapal's physical POS devices and there is no discussion of replacing this in V2. Card payment collection is expected to remain on the Pesapal hardware for the foreseeable future. The system will continue to record card as a payment method through manual confirmation, as it does in V1.

---

### The Direct Bank API Question

Gideon raised the question of whether Wendo could integrate directly with their bank's Mpesa API and cut Pesapal out entirely. This is a valid commercial consideration — Pesapal charges a transaction fee on every payment processed through their platform, so at scale, a direct integration would reduce costs.

The practical reality is that direct Mpesa STK push integration is available through Safaricom's Daraja API, which does not require Pesapal as an intermediary. Whether to go through Pesapal or directly through Daraja is a business and commercial decision for Wendo, not a technical limitation. Both routes achieve the same result from the customer's perspective. This question should be formally discussed and decided during V2 scoping before development begins, as it affects how the payment integration is architected.

---

### Per-Branch Bank Accounts and STK Configuration

A key requirement from Gideon is that each branch should operate with its own Mpesa till or paybill number, linked to its own bank account. The motivation is financial visibility — Gideon wants to be able to see exactly how much each branch is collecting independently, rather than all payments flowing into a single account and having to be reconciled manually afterwards.

In practice this means the payment module needs to support multiple Mpesa configurations within the system — one per branch. When a waiter at the Kingz branch triggers an STK push, the payment request goes through the Kingz branch configuration and lands in the Kingz branch account. When a waiter at the Town branch does the same, it goes through Town's configuration entirely independently.

This per-branch structure also means branch-level payment reporting becomes clean and automatic. The director can see each branch's collections in real time without any manual reconciliation, and the manager of each branch has full visibility into their own branch's payment activity.

---

### Open Questions for V2 Planning

1. **Pesapal vs. Daraja** — The decision on whether to integrate through Pesapal's payment API or directly through Safaricom's Daraja API needs to be made before architecture begins. This affects costs, technical complexity, and the onboarding process for adding new branches.
2. **Till number vs. Paybill** — Each branch will need either an Mpesa till number or a paybill with an account number. Which structure Wendo uses per branch will need to be confirmed as it affects how STK push requests are configured.
3. **Failed or expired STK push** — What happens in the waiter's app when a customer does not respond to the STK prompt or cancels it needs to be defined — whether the waiter can resend, switch to another payment method, or must escalate.
4. **Card payments long-term** — Whether Pesapal's POS devices remain the permanent solution for card payments or whether a software-based card option is desirable in a future version should be noted for long-term planning.
