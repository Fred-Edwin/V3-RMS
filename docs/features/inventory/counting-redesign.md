## What changes

1. **Many counts a day.** A count is its own record (scope, person, time, reference).
   Scope is whatever was counted (any sections or items). **Spot count is removed**; the
   Store Manager starts and logs a count the same way the Attendant does.
2. **Fixed structure, the Attendant chooses (final, 7 Oct).** All four sections are always
   shown with all their items in the same order; nothing is hidden or generated by the
   system (the movement-based list and key-items list were dropped as too clever). She
   decides what to count. **One action key whose label follows the box: a number typed
   reads "Next" (primary); an empty box reads "Skip" (neutral).** Skip is recorded as "not
   counted", no variance. **Zero is the 0 key, a real count of zero; the "None here" button
   is retired (7 Oct, owner: unclear copy, redundant with 0).** The Review screen lists every
   item with her number (tabs All, Skipped, Zero, Rechecked) and each number can be changed
   before signing. The old "every line needs a number" rule is gone: a count is what she counted. Each signed submission is one
   count, so several a day are fine.
   *Check once, at section end:* when she finishes a section, items that exceed the
   Manager's range show as "Check N items again" (no figures). Recount or Continue; after
   the one recheck nobody asks again. The review step stays (counted, skipped, None here,
   changed, rechecked), then PIN.
   *Staleness is shown, not enforced:* "Last counted 3 days ago" on sections and items
   (a date, not a stock figure), and the same across the store for the Manager.
3. **One counter at a time.** One open count, one person. No claiming sections.
4. **Sections stay supplier-based.** Manager owns the layout in Count setup. The Attendant
   may reorder sections for today only, and move an item to another section; the move
   applies at once, is logged, and the Manager sees it and can undo it.
5. **No "blind count" note on the Attendant's phone.** Blindness is still enforced on the
   server (`_shared/blind-rule.ts`); the screen just never shows a figure.
6. **The Manager is not blind.** Her own count shows expected stock.
7. **Variance flow (replaces accept, reason dropdown, send back, recount, resubmit).**
   - **Corrected 7 Oct (owner): nothing is hidden from the Manager.** The Manager sees
     every variance, whether or not it is within tolerance; the tolerance only labels it
     ("Within range" or "Exceeds") and decides what the Attendant is nudged about. The
     Manager sets the range herself as a percentage and a value (default **KES 500 and 5%**,
     both must hold to be within range). All stakeholders can see the result.
   - *Exceeds tolerance:* the Attendant is nudged to recheck that item at the shelf **before
     submitting**, with no figures and no direction. The recheck is optional: she may
     recount, or submit as she is. The latest count wins. Only big variations nudge her, so
     the screen stays quiet.
   - *Manager review:* all lines with their variance, within-range ones grouped and accepted
     in one tap, exceeding ones first, biggest value first, with the story under each line
     (for example "20 L went to Nyeri Town, dispatch not confirmed").
   - Within-range differences are **not** adjusted silently; they are accepted by the
     Manager (or by the system once she accepts the group) and logged like any other.
   - An item slightly short three counts running is flagged even inside the range.
   - Manager resolves each line in one tap: **log the missing movement** (fixes the record,
     no loss), **write off** with a cause chip (Prep use not logged, Spoilage, Miscount,
     Loss, Other with a note), or **ask for a recount** (the rare exception). Several lines
     can take one cause. One approval and PIN at the end.
   - Reasons are chips, never a dropdown. "Accept" and "Query" are retired as words.
8. **A count the Manager did herself:** inside tolerance needs no approval; anything outside
   tolerance is flagged to the Director.

## Access (one table, `central-store-access.ts`)

Every desktop role reads every counting, waste and ledger screen; write belongs to the job.

| Role | Read | Write |
|---|---|---|
| System Admin | everything | everything |
| Store Manager | everything | start and log counts, resolve variances, approve and sign, log and reverse any waste, Count setup and settings |
| Store Attendant (phone) | own count and own waste, never expected or stock figures | count, log waste, reverse own waste the same day, move or add an item |
| Director | everything, including variances and alerts | nothing (sets the Director alert amount) |
| Accountant | everything, with values | nothing |
| Branch Manager | counts, ledger, waste; no supplier payment details | nothing here |
| Department Head | not in this feature (branch waste is its own flow) | nothing |

Open: whether the Accountant sees variance reasons (recommended: yes, read-only).
