## What to build

Extends `backend/src/modules/inventory/receiving-*.ts`.

**Endpoints (plan §3.2):**
- `GET /inventory/ap/summary` — the Suppliers screen's 4 KPIs.
- `GET /inventory/ap/suppliers` — the how-overdue table. **Computed at query
  time, never cached** (plan §1.5) — five buckets always: `current`,
  `days1To30`, `days31To60`, `days61To90`, `days90Plus`
  (`AgingBucketsSchema` — this is the single source of truth; do not build a
  four-bucket variant anywhere, even for the detail screen, which only merges
  the last two **for display**, never in the query).
- `GET /inventory/ap/suppliers/:id` — profile, bucket panel, invoices,
  payments, purchase history. **Must reconcile exactly with the row this
  supplier gets on `/ap/suppliers`** — same underlying derivation, called
  twice, not two different calculations. Write the cross-check test named
  below before you consider this endpoint done.
- `GET /inventory/goods-receipts?status=RECEIVED_INVOICE_PENDING&supplierId=`
  — already exists from S4; confirm it serves the "receipts to bundle"
  picker correctly.
- `POST /inventory/supplier-invoices` — body includes `goodsReceiptIds[]`
  (≥1 — many-to-many via `SupplierInvoiceReceipt`, not a single FK) and an
  optional `dispute` object. **This one endpoint serves three UI outcomes**:
  plain save, save-with-dispute, and (client-side only) "Hold," which never
  calls this endpoint at all — do not build a second endpoint for the dispute
  case. Errors: 409 duplicate invoice number (scoped per-supplier, not
  globally — two suppliers may both issue "INV-001"), 409 receipt already
  invoiced, 400 receipts spanning different suppliers.
  **Compute `dueDate` here**: `invoiceDate + Supplier.paymentDays`, stored
  once at creation — never recomputed later even if the supplier's
  `paymentDays` subsequently changes (plan §1.3, §7 Q3(b)).
- `POST /inventory/supplier-invoices/:id/adjustments` — the Accountant's
  reconciliation adjustment. **Mandatory `reason`** — reject with 400 if
  blank, don't just make the field optional in the type and rely on the
  frontend to enforce it. Role: `ACCOUNTANT` + `STORE_MANAGER`. No stock
  ledger entry — if your implementation touches `InventoryTransaction`
  anywhere in this endpoint, that's wrong.
- `POST /inventory/supplier-payments` — body: `allocations[]` across one or
  more invoices. **Overpayment (Σ allocations < amount) is allowed, not an
  error** — the excess is never written to a stored balance; it's derived at
  read time as `Σ payments.amount − Σ allocations.amount` (plan §1.4, §1.5).
  Errors: 400 an allocation exceeds that invoice's current outstanding, 404,
  409 invoice already `PAID`.
- `POST /inventory/supplier-payments/:id/reverse` — **payments are
  immutable; there is no `PATCH`.** A reversal creates a *new* payment row
  with `reversalOfId` set and a negative allocation, mandatory `reason`.
  Never delete or mutate the original.

## Non-negotiables (restating — don't violate these)

- `organizationId` in every repository query; business logic in the service;
  DB access in the repository.
- Role table (plan §3.1): `STORE_ATTENDANT` is **403'd outright** on every
  endpoint in this session — not filtered, not given a narrower response,
  fully denied. Test this as a 403, not as an empty/null response.
- `ACCOUNTANT` can post payments and adjustments but must be blocked from
  every stock-moving or receipt-signing endpoint (separation of duties,
  `01-description.md` §2 — "the Accountant never changes what the ledger
  says is on a shelf"). This is worth a cross-module test, not just an
  assumption that RBAC on other endpoints already covers it.
- Zod on every input; TypeScript strict, no `any`.

## Test classification (plan §8)

- Invoice bundling across multiple receipts; duplicate invoice number → 409
  (scoped per supplier — test that two different suppliers can both use
  "INV-001"); receipts from two different suppliers on one invoice → 400.
- Partial payment → `PARTIALLY_PAID`; full → `PAID`; overpayment allowed,
  surfaces as a derived credit, never a stored column.
- Reversal restores the prior invoice status and is itself immutable.
- Aging buckets at boundary days: 0, 1, 30, 31, 60, 61, 90, 91 — off-by-one
  here silently misfiles a real invoice into the wrong collections-urgency
  bucket.
- **The three what-we-owe views reconcile** — one test that creates a known
  set of invoices/payments/adjustments and asserts the `/ap/suppliers` row,
  the `/ap/suppliers/:id` panel, and a straight sum of the underlying
  invoices all agree. This is the plan's §1.5 invariant; treat it as this
  session's single most important test.
- `STORE_ATTENDANT` → 403 on every endpoint in this file. `ACCOUNTANT` blocked
  from signing/ledger endpoints elsewhere in the module.
- Mandatory-reason enforcement on adjustments and reversals — a request with
  a blank or missing `reason` is rejected at the Zod layer, not just by
  convention.
