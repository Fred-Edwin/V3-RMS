## What to build

New files alongside Milestone One's in `backend/src/modules/inventory/`:
`receiving-repository.ts`, `receiving-service.ts`, `receiving-controller.ts`,
`receiving-routes.ts` (wired into `routes/index.ts`), plus their tests. (S4 and
S7 add to these same files — don't create per-session file names.)

**Endpoints (plan §3.2):**
- `GET /inventory/purchasing/summary` — three tiles: `expected{count,overdue}`,
  `awaitingInvoice{count,oldestDays}`, `owed{amount,over30Count}`. **Only
  `expected` is yours to compute for real this session** — `awaitingInvoice`
  and `owed` depend on `GoodsReceipt`/`SupplierInvoice` data that doesn't
  exist until S4/S7. Return `0`/`null` for those fields now (not an error, not
  fabricated data) and leave a comment pointing at the session that fills them
  in. Confirm this approach doesn't violate the frozen contract's shape before
  proceeding — it doesn't (the schema allows `oldestDays: number | null` and
  zero counts are valid), but say so explicitly in your own session notes.
- `GET /inventory/expected-deliveries` — query `status`, `supplierId`,
  `search`, `limit`, `cursor`. Serves the hub Inbound band, the Attendant
  worklist, and mobile.
- `POST /inventory/expected-deliveries` — creates an `AWAITING` record.
  **Writes no ledger entry** (plan §1.1 — this is the one fact every reviewer
  of this session should be able to verify by reading the service method: no
  `InventoryTransaction` import, no `$transaction` call).
- `POST /inventory/expected-deliveries/:id/cancel` — 409 if not `AWAITING`.
- `GET /inventory/purchasing/history` — a union of `ExpectedDelivery` and
  `GoodsReceipt` rows, one table, different fields per type. **This session
  can only return the `ExpectedDelivery` half** (no `GoodsReceipt` rows exist
  yet) — implement the union query shape now so S4 only has to add the other
  branch, not restructure the endpoint.
- `GET /inventory/items/:id/last-price` — feeds the New-purchase drawer's
  "Last purchase 2 Sep · KES 6,410" reference and the price-alert comparison
  S4 will need. In scope here since it only reads `InventoryItem`/existing
  ledger data, no new-model dependency.

**Reference numbers:** every `ExpectedDelivery` gets a generated `EXP-####`
reference via `ReferenceCounter` (plan §1.7) — increment inside the same
transaction as the create, never a separate read-then-write (that's the race
condition gap-free numbering exists to prevent).

## Non-negotiables (restating — don't violate these)

- Business logic in `receiving-service.ts` only. DB queries in
  `receiving-repository.ts` only. A `prisma.$transaction` in the service is
  allowed; plain reads/writes are not.
- Every repository query includes `organizationId` in the `where` clause
  (hub-org scoping, D-15 — Central Store data lives only on the hub org).
- Every route: `authenticate` + `requireRole`. Role table (plan §3.1):
  `STORE_MANAGER` full; `STORE_ATTENDANT` **read-only on expected deliveries,
  and the response must omit `estimatedTotal` (send `null`), not just hide it
  client-side** — this is a serializer-level rule, test it as one; `ACCOUNTANT`
  / `DIRECTOR` read-only.
- Zod schema (from `receiving-validators.ts`) on every input.
- TypeScript strict, no `any`.

## Test classification (plan §8 — new tests required from this slice)

- `POST /expected-deliveries` writes zero ledger rows (assert directly against
  `InventoryTransaction`, don't just check the response).
- `GET /purchasing/summary`'s `expected` tile counts correctly and marks
  `overdue` from `expectedDate < now()`, computed, never stored.
- `STORE_ATTENDANT` response to `GET /expected-deliveries` has
  `estimatedTotal: null` on every row; `STORE_MANAGER`'s does not.
- Reference numbers are gap-free under concurrent creates (a real test, not
  just a code-review claim) — two near-simultaneous `POST`s never collide or
  skip a number.
- Tenancy: cross-org isolation on every new endpoint.
- Cancel: 409 on a non-`AWAITING` record.
