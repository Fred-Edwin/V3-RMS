## What to build

Extends `backend/src/modules/inventory/receiving-*.ts` (S3's files) — same
module, not new files.

**Endpoints (plan §3.2):**
- `GET /inventory/goods-receipts` — query `status`, `supplierId`, `limit`,
  `cursor`.
- `GET /inventory/goods-receipts/:id` — the signed detail. Include the
  price-alert snapshot per line (not a live recompute — see below), the
  signature block, and the linked invoice (`null` / "Not recorded yet" until
  S7 exists — that's expected, not a bug to fix here).
- `POST /inventory/goods-receipts` — creates a **`DRAFT`**. **No ledger
  write.** If this session's implementation imports `InventoryTransaction`
  anywhere in the create path, that's wrong — delete the import, don't add a
  guard around it.
- `PATCH /inventory/goods-receipts/:id` — edits a draft only; 409 if already
  signed (`GoodsReceiptStatus` past `DRAFT`).
- `POST /inventory/goods-receipts/:id/sign` — **the one endpoint that writes
  the ledger.** In a single `prisma.$transaction`:
  1. For each line: one `InventoryTransaction { type: RECEIVE }` at the
     `CENTRAL_STORE` location, `quantity` in **usage units** (line's buy-unit
     quantity × the item's conversion factor — not the raw entered value),
     `unitCost` = the line's unit price.
  2. `InventoryItem.currentCost` ← that unit cost (latest-price costing,
     `01-description.md` §4 — the new price wins outright, no averaging).
  3. Status transitions to `RECEIVED_INVOICE_PENDING` or `RECEIVED_PAID`
     based on the receipt's `paymentTerms`, decided **once, at signing**, not
     re-evaluated later if the supplier's terms change.
  4. Notify the Store Manager (reuse existing notification infra, no new
     model — plan §3.3).
  If any line fails mid-loop, the whole transaction rolls back — no partial
  ledger writes, no receipt left in a half-signed state. Write a test that
  forces a failure on, say, line 2 of 3 and asserts line 1's ledger row was
  rolled back too.
  Errors: 401 bad PIN, 409 already signed / zero lines, 422 no
  `CENTRAL_STORE` location configured for the org.
- `GET /inventory/items/:id/last-price` — already built in S3; confirm it
  still serves this session's price-alert comparison correctly, don't
  rebuild it.

**Price-alert rule (plan §1.2 — read this twice):** when a line's entered
unit price exceeds the item's *current* last-purchase price by the configured
threshold, persist `priceAlertPct` and `priceAlertPrevPrice` **on the line, at
save time** — not computed live on read. By the time this receipt is read
back later, `InventoryItem.currentCost` has already moved on to this
receipt's own price (from the signing transaction above), so a live
comparison would either compare against itself or require a separate price-
history join that doesn't exist. If `acceptedPriceAlerts` includes this
line's id at sign time, also stamp `priceAlertAcceptedById`.

## Non-negotiables (restating — don't violate these)

- The ledger write and the status transition happen in the **same**
  transaction as each other, in the **sign** endpoint only — never split
  across two requests, never in `create`/`PATCH`.
- Business logic in the service; DB queries in the repository; `organizationId`
  in every query.
- Every route: `authenticate` + `requireRole`; `STORE_MANAGER` and
  `STORE_ATTENDANT` both have full access here (unlike the Supplier-AP
  endpoints S7 builds, where the Attendant is excluded).
- Zod on every input; TypeScript strict, no `any`.

## Test classification (plan §8 — this session's tests are the ones the plan
calls out by name)

- Signing writes the ledger **exactly once**, atomically — a failure mid-
  transaction leaves zero `RECEIVE` rows and the receipt still `DRAFT`.
- Latest-price costing updates `InventoryItem.currentCost`; buy→usage unit
  conversion is applied correctly (test the exact case from the plan: 18.0 kg
  entered against a `crate (12)` buy unit).
- The price-alert snapshot survives a later price change — sign a receipt
  with an alert, then sign a second receipt at a different price, then read
  the first receipt back and assert its stored `priceAlertPrevPrice` is
  unchanged.
- `DRAFT` receipts write no ledger rows — assert directly against
  `InventoryTransaction`, not just the response shape.
- Payment-terms branch: `PAY_NOW` → `RECEIVED_PAID`, no AP implication (S7
  will build on top of this later, but confirm no orphaned invoice record is
  created here). `INVOICE_TO_FOLLOW` → `RECEIVED_INVOICE_PENDING`.
- Tenancy and role tests, same pattern as S3.
