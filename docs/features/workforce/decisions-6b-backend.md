# Workforce segment 6, back end B: decisions (20 Oct 2026)

Additions and departures while building the audit read side, the documents door and the verify endpoints. Specs: `specs/6a-...`, `specs/6c-...`.

| # | Question | Choice | Why | What changing it takes |
|---|---|---|---|---|
| B1 | How does the list stay fast on a very large log? | It reads the entry index (`workforce_audit_entry_index`), which gains copied `category`, `actor_id`, `subject_user_id` columns and indexes on them, plus a trigram index on `search_text`. The page then fetches its 25 to 100 full entries by id. | The append-only table cannot be altered or indexed freely. | A new index in a migration. |
| B2 | Exact counts. | Counted up to 50,000 with `LIMIT 50001`; above that `totalIsExact:false`. | Spec SD6. | The `COUNT_CAP` constant. |
| B3 | Deep pages. | Past page 200 a range wider than 90 days answers 400 `RANGE_REQUIRED` ("Choose dates to go further."). Offset paging, not keyset. | The simplest thing that cannot scan years. | Keyset paging. |
| B4 | Which event holds LOG_ACCESS and SENSITIVE_VIEW? | LOG_ACCESS with Security, SENSITIVE_VIEW with People. | Every category belongs to one Event menu item (tested). | The map in `audit-visibility.ts`. |
| B5 | Out-of-scope reads. | A category or site the reader may not read is dropped inside the query: empty list, zero count. A reader with no category gets 404. Entry detail outside scope is 404. | A count must not leak. | None. |
| B6 | "Log viewed" once per 10 minutes. | A one-row-per-reader mark table updated by a conditional upsert, in the same transaction as the `audit.log_viewed` entry. | Safe under two page loads at once. | `LOG_VIEW_WINDOW_MS`. |
| B7 | CSV. | Streamed in 1,000-row batches, entry written before the first byte, leading `= + - @ tab CR` get a quote, BOM, Nairobi times; no hash, device or place. | Spec A4. | `csv.ts`. |
| B8 | Chain check. | `verifyRange` reads 5,000 at a time, one check a minute per reader, 200,000 entries a call. A break writes one `audit.chain_failed` with its alert (once an hour per entry) and tells the System Admins and the Director. Nightly: last 2 days, whole chain on Sundays. | Spec A3, A6. | The job schedule. |
| B9 | Rate limiter. | `_shared/limits/rate-limit.ts`: Redis counter, falls back to a per-process counter when Redis fails (30 s cool-down). | Redis may be down; the verify page must still be limited. | None. |
| B10 | Index for entries older than the index. | `backfillAuditIndex` (nightly, idempotent) writes index rows for older entries with the same wording function. | The migration fills only existing index rows. | None. |
| B11 | Entry detail `signature`. | Always `null` for now. | No writer records the signing method on an entry yet. | The writer storing `method:'PIN'` in `after`. |
| B12 | Activity on my record. | Own rows only (`subject_user_id = me`), never LOG_ACCESS, hides `security.payslip_unconfirmed_phone` (the System Admin's copy). Default range is this month. One answer per entry; "That was me" writes `audit.record_answered`; "This wasn't me" calls back end A's `wasntMe`. | Spec A8. | Chip map in `my-record-wording.ts`. |
| B13 | Digest range. | `GET /payslips/opens` with `from`/`to` (max 31 days) returns `{days:[{day,rows}]}`; `day` or nothing keeps the old list. Rows gain `firstAt`, `lastAt`, `many` (over 150). Spans are kept on the digest row (two new nullable columns). | Spec A9, compatible. | None. |
| B14 | One payslip hash. | `_shared/documents/qr-hash.ts` `payslipContentHash`; both payslip renderers print its first 10 characters. The old payroll-export hash (a hash of the snapshot) is replaced, so QR codes already printed from the month export before this change no longer match. | Spec X4 asks for one hash. | Not reversible for printed copies; none are in production yet. |
| B15 | How are existing issuers indexed? | Not inside their transactions (would touch five issuing services). Each registers a read-only **source**; `reconcileDocuments` writes through `registerDocument`: at deploy/nightly, before an index read (5 min fresh) and on a verify miss (1 min fresh). | Fewer edits to working payroll code. A document is verifiable within a minute at most. | Calling `registerDocument` from each issuer. |
| B16 | Door signature. | `registerDocument(tx, input)`, `withdrawDocument(tx, {companyId, number, byRole, at, replacedByNumber?})`. Same number and version with another hash: 409. A title or period that looks like money: 400. | Spec D1. | None. |
| B17 | Visibility of documents. | By the type's capability and scope from the access table (`readableKindsOf`). The System Admin's `payroll.read` still lets them see PAY (gap noted in the spec, not changed here). | No new role lists. | The access table. |
| B18 | Verify outcomes. | Public: GENUINE, REPLACED, WITHDRAWN, ARCHIVED, NOT_VERIFIED (unknown number and wrong hash are one answer, recorded as two), MALFORMED, RATE_LIMITED (429). Only 15 named keys can leave (tested). | Owner decision O3, spec D3. | `PUBLIC_KEYS`. |
| B19 | Limits. | 30 a minute and 300 a day per address, global 600 a minute. Each check is a counter row; signed-in genuine checks write `document.verified`; a wrong hash on a real number writes at most one `document.verify_failed` per number per day. | Spec SD27. | Constants. |
| B20 | Capabilities. | None added; the log uses the per-category read capabilities and `audit.verify_chain`, the index uses each type's capability, signed-in verify needs only sign-in. | The table already holds them. | The table. |
