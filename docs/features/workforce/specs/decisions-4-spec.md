# Segment 4 (Leave): spec decisions

20 October 2026. Written by the spec session for `4-leave-spec.md` and `4-leave-spec-screens.md`. Each row is a question Paper or the built code left open, my recommendation (already written into the spec), why, and what changing it takes. The spec cites rows as L1, L2 and so on. Rows marked **Owner** repeat a decision the owner already made. Nothing here is built yet.

| # | Question | Choice | Why | What changing it takes |
|---|---|---|---|---|
| L1 **Owner** | Where is leave decided? Paper step 9 still draws the "Waiting for you" page. | **Only on the Leave page, with the rota in front of the manager** (Paper steps 10 to 12). Waiting for you no longer exists (design pass 4), so step 9 is **not specced as a screen**. The spec covers three things instead: the numbered badge on the Leave menu link, the Leave rows on the Branch Manager's Home "Needs you" card (the card is segment 6's; the spec says what it expects), and the Leave page. Overtime and clock fixes are not part of this segment. | Owner message, 20 Oct 2026, quoting design-pass-4. | Nothing: it is a rule. |
| L2 | Which sites are handled by the new Leave and which by the old HR leave screens during rollout? | **The same per-site switch as Attendance** (`attendance_site_switches`, System Admin only). Switch on: the site's people use the new Leave and the old leave routes refuse writes for that site. Switch off (the default): nothing changes, the old screens stay. | Leave days feed the rota, the Today board, timesheets and payroll, which are all on that switch. A second switch would allow a site on the new rota but the old leave, which double counts days. | A separate `leave` switch row and a second guard. |
| L3 | How is one request never decided twice, in two systems? | At switch-on a **one-way, repeatable carry** copies the site's open and future legacy requests into the new tables (idempotent by `legacy_request_id`). The old leave write paths (submit, approve, reject, cancel, revert, balance update) get one additive guard line that answers `409 LEAVE_IN_NEW_SYSTEM` for a switched-on site. Legacy tables and their data are never edited. A carry run re-reads: a legacy row decided in the gap between the switch and the first carry updates its still-waiting new copy to match. | The attendance switch already does the same with the clock; the pattern is proven. | A guard in the database (trigger) instead of in code. |
| L4 | What happens to old requests and balances? | **Requests:** legacy requests ending today or later, plus the current year's decided ones, are carried as history (`origin = LEGACY`, keep their old day counts, marked "counted in working days by the old system"). **Balances:** one `OPENING` ledger entry per person and type = legacy `total_days - used_days` on the carry day. Carried requests are never counted again in new balance maths (they are already inside the opening). Rules' days apply from the next leave year. | A person must see the same days left the day after the switch. | Recount all history in calendar days (not recommended: it changes what people were told). |
| L5 | Rollback (switch off). | Approved or waiting requests made in the new system that have not ended are **mirrored back** as legacy rows (marked, so a later switch-on does not carry them again) and the old routes work at once. Slips already issued stay valid. | Same rule as the clock: turning a site off must not lose a decision. | Block switch-off while any new request is open. |
| L6 | Which days count? | **Every calendar day** from the first to the last day, inclusive, Sundays and public holidays included (owner rule, Paper step 2 footer). The old system counted Monday to Friday only. | Wendo works seven days a week. | Not changeable without a Rules setting; none is planned. |
| L7 | How is a year's entitlement built from the Rules Leave tab? | Per type: `daysPerYear` (or the `defaultPolicy` figure when that is empty, else 0) from the Rules version in force **on the first day of each month it is credited for**. `UP_FRONT`: the whole figure from 1 Jan, or the start date for a joiner, no proration. `MONTHLY` (Annual 1.75): credited on the 1st of each month **starting the month after the start month**; days earned so far = floor(sum of monthly credits), so nobody is promised a part day. `PER_EVENT` (Maternity, Paternity): nothing until HR adds the days (Paper step 15). The old per-contract `LeavePolicy` is not used by the new system. | Matches Paper's Joy Chebet (joined 14 Jul, 5 days left on 9 Oct: Aug, Sep, Oct = 5.25, floor 5). Computed on read, so no monthly job can fall behind. | Switch Annual to "All at the start" in Rules, one Change, no code. |
| L8 | Paper shows Cynthia with 12 days left of 21 on 9 Oct, which is "all at the start" maths, yet Rules says Annual builds up 1.75 a month. | **Build follows the Rules setting.** With 1.75 a month a long-serving person on 9 Oct has about 17 earned. Paper's figures are sample data. The owner can pick the other model with one Rules change. Flagged in the final message. | The setting exists so the owner decides, not the code. | Same as L7. |
| L9 | Carry-over. | On first read of a new leave year the service writes one `CARRY_OVER` entry per person and type = min(closing balance of last year, `carryOverDays` in force on 1 Jan). Idempotent by (person, type, year). No expiry date. | A job would add a worker dependency; the first read does the same work safely. | Add an expiry or a Rules "use by" date. |
| L10 | Can a request cross 31 December? | No. "This runs into next year. Send two requests." Each leave year has its own balance. | Keeps frozen balances and slips simple. | Split automatically by year. |
| L11 | How much does a request check? | Days asked must not exceed **days left now** (earned so far minus taken minus booked). Waiting requests are not subtracted (Paper: "left now 12, if approved 9"), so the decider checks again at the moment of approval. Days not yet earned cannot be booked. | One number everywhere. | Check against days earned by the leave's start date. |
| L12 | Not enough days (Paper step 8). | The staff member may send **one request with an unpaid tail**: "5 annual + 2 unpaid" (`unpaid_tail_days`, the last days of the range). One request, one decision, one slip that says both. Any limited type may do it. | Paper offers it; a split into two requests would need two decisions. | Two linked requests. |
| L13 | Unpaid leave as a chip on the request screen. | Added as a fourth chip "Unpaid" (needs a reason), beyond Paper, because Rules has the type and staff must be able to ask for it. Maternity and Paternity show as chips only when the person has days. | Production need. | Remove the chip. |
| L14 | Reason field on the request. | Paper has none. Production adds a one-line note: **required** when the type's `requiresReason` is on (Emergency, Unpaid), otherwise optional. | The Rules type table says "A reason". | Remove the field. |
| L15 | Minimum cover: blocks or warns? | **Warns only** (Paper and Rules card: "It never blocks"). The manager sees days and numbers; the staff member sees only a plain amber line with no numbers. | Owner rule; a manager may have a reason. | A Rules switch "block below minimum". |
| L16 | How is cover counted? | Per department, per day of the request: people who would be working = if the rota is planned for that day, rostered people minus this person if rostered, minus anyone on approved leave; if the rota is not planned yet, the department's active people minus anyone on approved leave minus this person ("usual shifts"). Compared with the Rules minimum for the department (site override first). | Matches Paper steps 10 and 16. | A different definition of "working". |
| L17 | What does approval write? | One transaction: the application becomes APPROVED, the slip number LVE-n is issued and the slip snapshot frozen, the person's rota cells on those days are **removed** (so the rota shows Leave), balance before and after are stored, the audit entry is written. Then: the person and the department head are told; the Today board, Home "On leave" cell and "Coming up" card read the approved days. | Paper step 11: "26, 27 and 28 Oct become Leave". | Keep the shifts and show leave beside them. |
| L18 | Who decides? | Staff and heads: the Branch Manager of the person's site (Store Manager for the Central Store). A manager's own leave: HR. HR's own: the Director. The Director's own: HR. Head office staff and the Accountant: the Director. Types set to "approved by HR" (Maternity, Paternity) go to HR from the start. After **3 days (72 hours)** unanswered the request moves to HR; the Branch Manager can still not decide it then. | Paper steps 5 and 13, plus the gaps Paper does not draw. | A Rules setting for the 3 days. |
| L19 | May HR decide before the 3 days? | **No**, except a manager's own request and Maternity or Paternity. Before then HR sees the request with Approve disabled and the reason "With the Branch Manager. It moves to HR on Sun 12 Oct, 15:10." | One decider at a time. | Allow HR any time. |
| L20 | The 3 days: how is it applied? | The stage is **derived** from the ask time (72 hours), so it is right even if the worker is down. An hourly job only writes the "moved to HR" event, the audit entry and the notifications. The 72 hours is a code constant, not a Rules setting (Paper's card is fixed text). | Same robustness choice as the timesheet month state. | Move the constant to the Leave rules group. |
| L21 | Two deciders at once, double taps. | Every decision sends `expectedVersion` and a client `Idempotency-Key`. The second decider gets `409 ALREADY_DECIDED` naming who and when; the same key returns the first result. Creating a request uses a key too, so a retry never makes two. | Never silently overwrite. | None. |
| L22 | A request that spans a rule change. | The leave type's name, pay flag and approver are **frozen on the request when it is asked**. Days are always calendar days. Minimum cover is read at decision time. Balances use the rule version of each month. A Rules change never re-counts leave already approved (Rules dialog says so). | Past leave must stay explainable. | None. |
| L23 | Cancelling. | The person may cancel while waiting, or while approved and not started. The manager (and HR) may cancel an approved request that has not started, with a reason and a PIN, because it voids a signed slip. A leave in progress or finished cannot be cancelled (Paper step 13 note); HR adjusts the balance if someone returns early. Rota days stay empty after a cancel and the Branch Manager is told. | Paper. | Add "Cut short". |
| L24 | The decline dialog has no PIN in Paper. | **No PIN to decline** (nothing is signed, no balance moves, the person may ask again). Reason chip required, note optional (required for "Other"). Approve needs a PIN. | Keeps declining quick and the signature meaningful. | Add a PIN field. |
| L25 | The adjust dialog has no PIN in Paper, the brief and every other pay-affecting change has one. | **PIN required** (signed act). Reason chip required, note required for "Other". An extra chip "Birth or adoption" is added (Maternity and Paternity days are granted this way). | A balance is worth money. | Remove the PIN. |
| L26 | Who adjusts balances? | HR Manager only (new capability `leave.balance_adjust`). Whole numbers from -60 to +60, never below 0 days. The Branch Manager and Director read. | Paper: "the only place a balance is adjusted". | Grant to the Director. |
| L27 | Slip number. | `LVE-nnnn`, issued **at approval** from a database sequence (gaps allowed, like TSH-n), four digits padded and growing past 9999. A request that is declined or cancelled before approval never gets one. A cancelled approved request keeps its number and the slip is re-rendered with a CANCELLED stamp. | Same as the timesheet and payslip numbers. | Per-year numbering. |
| L28 | Slip content and the QR. | The slip text is a fixed template filled from a frozen snapshot (same bytes on re-render). The QR carries `{FRONTEND_ORIGIN}/verify/lve/{number}?h={hash prefix}`, the same shape as `/verify/ps/`. The verify page is segment 6's and will show only: valid or not, number, issue date, issuer's role, approved or cancelled. | Consistent with payslips. | None. |
| L29 | "Ms" and "Mr" on documents (Paper's slip says "Ms Cynthia Wairimu"). | **No titles.** The slip addresses "Cynthia Wairimu". | A title guesses gender; the owner's wording rule avoids it. | A title field on the person file. |
| L30 | Notifications and balances. | A push or lock-screen text never carries a balance, dates beyond "your leave request", or a name: "Your leave request has an answer." The in-app Inbox row may carry days left, since it is seen after unlock. The Paper wording table's "leaveAsked ... In Waiting for you" and names are replaced (spec sets the new wording). | Owner brief. | Show less in the Inbox. |
| L31 | Menu badge. | The Leave link carries a number: Branch Manager and Store Manager = requests waiting for them; HR = requests with HR (moved or own-type) plus managers' own; Director = requests routed to them. Staff have no badge (their Inbox has it). | Replaces Waiting for you (L1). | None. |
| L32 | Retroactive leave (someone calls in sick today and the day is already past). | Not in this segment: the date picker starts today (Paper: "Earlier dates can't be picked"). A past absent day is decided in Timesheets. Logged as a gap with a recommendation to let HR record leave on a person's behalf in a later session. | Paper is explicit and a second entry path needs its own design. | A new HR "Record leave" dialog. |
| L33 | Unpaid leave and payroll. | The approved days (paid and unpaid, with the unpaid tail) are handed to timesheets as `leaveDays` and to the month snapshot as `paidLeaveDays` and `unpaidLeaveDays`. Payroll turns unpaid days into the existing `UNPAID_ABSENCE` line using `unpaidDayDivisor`. This needs a small additive change in the snapshot and payroll inputs (listed as a gap). | The divisor already exists and nothing feeds it from leave. | None. |
| L34 | Who may see what. | Staff: own requests only. Heads: no Leave page (Paper draws none); they are told when their people are away and see Leave on the rota and Today board. Branch and Store Managers: own site, requests, calendar, balances read-only. HR: all sites, plus adjust. Director and System Admin: all sites, read, and decide only as fallback. Accountant: no access (payroll reads days through the door). | Access table plus Paper. | Edit the grants and the matrix test. |
| L35 | Waiting-day wording of the old Home cards. | The Home "Needs you" leave row is specified here but **built by segment 6**. The Leave page opens from it with the request selected (`?open=id`). | L1. | None. |
