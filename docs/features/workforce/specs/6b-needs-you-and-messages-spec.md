## N5. Sources, the registry and what Leave and Conduct must supply

**How it is built.** No stored "waiting" table. Each source lists and counts from its **own** table, so an answered item disappears by itself and nothing drifts. Back end: `modules/workforce/needs-you/` with `sources/<name>-source.ts` exporting `{ id, kinds, list(subject, ctx), count(subject, ctx) }` registered in `sources/index.ts` (an empty list is valid, so Segments 4 and 5 register theirs without touching this file), `needs-you-service.ts` (merges, orders, caps at 500, tags emphasis from `lastSeenHomeAt`), routes with `requireCapability('needs_you.read')`. A source filters by the **action** capability, never by role name (`overtime.approve`, `timesheet.close`, `payroll.approve`, `leave.approve`), so the access table stays the one authority. Front end: the card is `workforce.needs-you`; its data hook calls `GET /workforce/needs-you`; the Home registry (`home/README.md`) draws it and the empty rule hides it.

**Card ids that change** (`chapter-1-ledger.md`): `workforce.waiting-for-you.desktop` becomes `workforce.needs-you`; `workforce.waiting-for-you.phone` is deleted; `workforce.overdue-approvals` becomes `workforce.overdue`; `workforce.hr-kpis` and `workforce.branch-kpis` rename the cell Waiting for you to Needs you; `workforce.hr-attention` loses its leave and Report-a-problem rows (they move to Needs you) and keeps finish hiring, probation ends, no head; `workforce.payrun-steps` is retired (its steps are the Payroll rows above; the rule confirmation is the Tables row); `workforce.payrun-kpis` stays; new `workforce.payslip-openings`. Menu rows: `wf-waiting`, `wf-overdue`, `wf-head-waiting` are removed from `WORKFORCE_ROWS`; new row `wf-security`; rows `wf-leave` and `wf-conduct` stay `notBuilt` until their segments (a badge on a hidden row is dropped by the table).

**What the rows that wait for Leave and Conduct assume.** *Leave (Segment 4)* registers `leave-source` returning `{ id: 'leave:<requestId>', kind: 'Leave', person, role, type, from, to, days, siteId, waitingSince, waitingOnRole: 'MANAGER'|'HR_MANAGER'|'DIRECTOR', href: '/app/workforce/leave?request=<id>' }`; it must (1) move a request to HR after 3 days unanswered and record `Moved to HR after 3 days`, (2) send a Branch Manager's own leave to HR, (3) say who holds HR's own leave (assumed the Director) and (4) emit `leave.requested`, `leave.decided`, `leave.moved_up` events for the socket nudge. *Conduct (Segment 5)* registers `conduct-source` for **appeals** only (`{ id: 'appeal:<id>', person, noticeNumber, waitingSince, href }`, HR only) and emits `conduct.appeal_sent`, `conduct.appeal_decided`; a notice waiting for the person's signature is the person's own Inbox row, not a Needs-you row. Neither segment may add a row kind without a line in the table of N1.

## N6. Delivery of "told", and the Inbox (SD23)

Today `getWorkforceNotifier()` only logs ("not delivered yet"), so **no "is told" row in any approved segment reaches anyone**; this segment makes it real.
- **Store:** `workforce_notifications` (`id`, `userId`, `kind`, `tone` (`information|changed|needsLook|done|problem`), `title`, `body`, `href`, `createdAt`, `readAt?`). The wording is rendered **on the server at send time** from one table `_shared/notification-wording.ts` (moved from the front end's `notification-copy.ts`, which becomes the gallery and keeps a test that both agree), so a stored row never changes and a push body is the same text. Never a pay figure; names only with a role.
- **Channels:** an FCM push through the existing push service (one per device; `title`, `body`, `href`); the socket nudge `workforce:notifications` (no payload) to the user's room; and the Inbox row. **Quiet hours:** an `information` push from 22:00 to 05:00 Nairobi is held (a delayed job) and the Inbox row appears at once; every other tone goes at once, and `problem` is high priority (SD13).
- **Inbox:** the existing Inbox page (messages, broadcasts, notices) gets one **Notifications** tab, first, with a dot when unread. Rows use the built `InboxRow` (3 px tone bar, title, text, mono `time · AREA`, brown action button where `href` is set, brown 8 px unread dot) and an amber `Mark all read` in the header (Paper step 30). The shell's Inbox badge adds the unread notification count. Opening a row marks it read; `Mark all read` marks the page.
- **Endpoints:** `GET /workforce/notifications?unread=&page=`, `GET /workforce/notifications/unread-count`, `POST /workforce/notifications/read { ids }`, `POST /workforce/notifications/read-all` (own only). Delivery is best effort: a failure is logged and never fails the change (`told()` keeps this rule); duplicates are prevented by a `dedupeKey` per kind, subject and window (`overdueReminder` once per item per day, `payslipOpenedByStaff` once per opener per day, alerts once per 15 minutes).
- The legacy Inbox, its broadcasts, direct messages and formal notices are untouched.
