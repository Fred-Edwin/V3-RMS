# Segment 1B (Rules): spec decisions

19 October 2026. Written by the spec session for `1b-rules-spec.md`. Each row is a question Paper or the built rules store left open, my recommendation (already written into the spec), why, and what changing it takes. The spec cites rows as D1, D2 and so on. Rows marked **Owner** repeat a decision the owner already made. Nothing here is built yet.

| # | Question | Choice | Why | What changing it takes |
|---|---|---|---|---|
| D1 | The dialog says "told, with old and new". The brief says never pay figures in notifications. | A notification for a change to a **pay field** (overtime multipliers, holiday pay rate, statutory tables, casual daily rates, the deduction cap) says which tab and row changed and from when, with **no numbers**. Changes to non-pay fields (grace minutes, windows, leave days, months, week start) may show old and new. The dialog caption is generated from the same flag: "are told it changed" for pay fields, "are told, with old and new" otherwise. The audit log keeps the figures for the roles that may read it. | Inbox and push can be seen over a shoulder or on a lock screen. | One flag per field in `rules-field-policy.ts` (`pay: true`) and the caption function. |
| D2 | Overtime Paper says "if the Director changes the multiplier, the old one stays in use until the Accountant confirms the new one". The built store makes payroll **refuse** an unconfirmed pay rate. | **Paper wins.** A pay field resolves to the newest version of it that is confirmed (or carried forward as confirmed). Until the new one is confirmed the old value stays in use. If no version was ever confirmed, payroll refuses (as built). Once confirmed, the new value applies from **its own effective date** to every month not yet approved. | The owner approved the box text. A pay run must never stop because someone has not clicked yet, but it must never use an unchecked rate. | The resolver in `rules-service.ts` (`resolveGroup`) and `isPayConfirmed`. |
| D3 | Statutory Paper shows rates "applying from" past dates (1 Oct 2024) and a version 4 confirmed on 19 Oct 2026 for 1 Feb 2026. The built store refuses any start date in the past. | **Only the Statutory tab** may start on a past date, and never earlier than the first day of the **earliest month that is not yet approved** (so it can never alter an approved month). Every other tab keeps "today or later". The first entry into the empty store may therefore start up to the open month's start. | The Accountant has to type rates that already apply. The sample dates in Paper are illustrative (owner rule), so the screen need not offer 2024. | The date rule in `createVersion` (one group flag) and the picker's `minDate`. |
| D4 | Holidays: Paper step 13 says the Director edits the list and confirms it, the Accountant edits and confirms the pay rate, HR reads. The access table lets HR edit holidays and gives the Director only the list confirm. | **Paper.** Director: edit and confirm the list. Accountant: edit and confirm the pay rate (new capability `rules.edit.holiday_pay`). HR and the Branch Manager read. | Paper step 10 and the version-13 table agree with each other; the code comment predates them. | One table, `workforce-access.ts`, plus `rules-field-policy.ts` (`payMultiplier` edit capability). |
| D5 | Leave: one capability `rules.edit.leave` covers leave types and minimum cover. Paper: HR changes leave types, the Branch Manager (own site), Director or System Admin change minimum cover, HR reads minimum cover. | Split into `rules.edit.leave_types` (HR) and `rules.edit.min_cover` (Branch Manager and Store Manager at unit scope, Director, System Admin). The Director does **not** change leave types. | Paper steps 18 to 20 and the owner's design pass 2. | The access table and the field policy (`leaveTypes`, `defaultPolicy` to the first; `minimumCover` to the second). |
| D6 | System Admin: the table gives lateness, overtime and attendance edits; Paper never lists the System Admin on those tabs. | System Admin **reads** every tab and changes **only minimum cover** (Paper step 18). The three other grants are removed. | A technical role should not set pay-affecting rules, and Paper's "Who changes it" panels say so by omission. | Add the three rows back to the System Admin grants. |
| D7 | What number is "Save as version N"? | One more than the highest version number of that group **and scope** (company, or that site). The preview endpoint returns it. A site override has its own count. | Matches `createVersion` (`number = latest + 1` per scope). | None. |
| D8 | Two people change the same rule at once. | The dialog sends `expectedVersion` (the version the screen showed). If the scope has a newer version the server answers `409 RULE_STALE` with the new version; the dialog stays open, shows "Someone changed this rule a moment ago", shows the new NOW value, keeps what was typed, and the PIN is cleared. | Never silently overwrite. | Make `expectedVersion` optional. |
| D9 | A date that clashes with a version already stored (built: not before the latest version of the scope; same date gives a higher number). | Kept. The picker's earliest day is the later of today and the latest stored version's date. A **scheduled** version can be withdrawn (D22) to free the date. Copy: "Version 3 already starts on 2 Nov 2026. Choose that day or later, or withdraw version 3 first." | Rules versions are a single timeline per scope. | Allow several scheduled versions and re-sort them. |
| D10 | Default start date in the dialog. | **First day of next month** for a field that changes pay (lateness, overtime, casual rates, statutory, holiday pay); **today** for everything else (attendance, leave, probation, conduct, week start, minimum cover). Paper's samples (2 Nov, 1 Jan 2027, 19 Oct) fit this. The person may pick any day from the earliest allowed. | Pay changes start on a month boundary so one month never mixes two rules; operating rules should take effect at once. | A constant list of "pay fields". |
| D11 | A change that would alter a month already approved or paid. | **A change never alters an approved month.** Approval freezes that month's rule values (Segment 1A snapshot); payroll for an approved month reads the snapshot. A version dated inside an approved month still saves and shows "Months already approved: Not changed" in the dialog; it applies to months not yet approved. For Statutory a date inside an approved month is refused (D3). | Owner rule from the review; an approved month must always be explainable. | The month snapshot is a 1A/Segment 2 dependency; until it exists the preview row says "Not changed" and the server refuses Statutory dates before the open month. |
| D12 | "What it would have changed in September" (Lateness dialog) and the "Notices already issued" rows (Conduct) | The preview endpoint returns up to 3 **impact rows** (label, value) computed per field kind, then the fixed "Becomes" row. Computed ones: Lateness grace, policy and cap (late marks of the last completed month, counts only); Overtime window and caps (items that would change status, counts only); Leave type days ("86 people on the leave policy", "Leave already taken or booked: Not changed"); minimum cover ("Requests waiting now: 0 in Pastry are affected"); Conduct months ("Notices already issued: Keep their old end date"); Probation (people currently on probation, counts). A field with no honest calculation returns no impact rows (never a made-up line). | Paper draws the rows; production must compute them or leave them out. | The impact functions in `rules-impact.ts` (new). |
| D13 | Units: Paper shows "3 days" for the excuse window and the authorise window; the store keeps hours. | The screen shows whole days when the hours divide by 24, otherwise hours. The dialog asks in days (1 to 30) for both; the server keeps hours (`days × 24`). | Matches Paper without a data change. | Change the schema to days. |
| D14 | Holidays `enabled` flag is on no screen. | The server sets `enabled = payMultiplier !== null` on every Holidays version; the screen never shows it. | One fewer switch to get wrong; Paper has none. | Show a row "Pay extra on holidays: On / Off". |
| D15 | Holiday list: Paper shows only "still to come in 2026" and a Change per row. | The tab shows a year selector (`SegmentedControl`, current year and next), default the current year. Past dates are listed greyed with no Change ("Past"). Change on a row edits date and name, with a text button **Remove this holiday**. An outlined **Add a holiday** sits under the table (Director only). | A list must be added to and corrected. Beyond Paper; reported. | Drop the year selector. |
| D16 | Casual rates: Paper keys them by department ("Kitchen and Pastry", "Central Store"); the schema keys them by `positionId`. | Rates are keyed by **department** (`departmentId`), and the schema changes accordingly. "Per hour over 8" is shown to 2 decimals (112.50, not 112): Paper truncates, and rounding is a payroll rule (Segment 2). | Paper lists departments. | Revert the schema key. |
| D17 | Probation Paper rows not in the schema ("Reminder to HR before it ends 14 days", "Reports before the decision: day 45 and day 80"). | Add `reminderDaysBeforeEnd` (default 14) and `reportDays` (default [45, 80]) to the Probation schema. | The owner approved those rows. | Hide the two rows. |
| D18 | Leave type columns in Paper (Builds up, Pay, Also needs). | Add to each leave type: `accrual` (`UP_FRONT`, `MONTHLY`, `PER_EVENT`) with `perMonthDays` for monthly, `carryOverDays`, `sickNoteAfterDays`, `approvedBy` (`MANAGER` or `HR`). `paid` stays. Maternity and Paternity are `PER_EVENT` and approved by HR. "Add a leave type" is built (brown button, as drawn). | Paper shows these columns. | Drop the columns. |
| D19 | Overtime multipliers: Paper lists ordinary day 1.5, rest day 2.0 and public holiday 2.0; the schema has `standard`. Holidays also holds a pay rate. | `multipliers` becomes `{ ordinaryDay, restDay }`. The public-holiday figure on the Overtime row is **read from Holidays** (`payMultiplier`) and labelled "public holiday 2.0 × (set in Holidays)". One number, one place. | Two places to type the same pay rate would drift. | Add `publicHoliday` to the overtime multipliers and drop it from Holidays. |
| D20 | The Branch Manager's own view of Lateness and Overtime and minimum cover (not drawn). | Built beyond Paper in the same style: header "Rules · Lateness · Nyeri Town", values are the site's effective values, rows that are the site's own say **Own rule** in amber, company-only rows (deduction cap, multipliers) show a padlock. The Statutory tab shows the locked card. | Owner decision in the review. | None. |
| D21 | How does a Branch Manager give an own rule back? | A text button under the row, **Use the company rule again**, saves a site version with **no fields** (an empty override). The service accepts `{}` for a site scope only for this. | Otherwise an override is forever. | Remove the button. |
| D22 | Withdrawing a scheduled version (Paper step 12). | A **withdrawal row** (`RuleVersionWithdrawal`: version, who, when, reason) marks it; the version stays listed as "Withdrawn"; the resolver skips it. Only the people who may change that tab, and only before its date. Needs a reason and a PIN. Same people told. | Versions are never deleted. | Remove the button. |
| D23 | Statutory ships empty. What does the Accountant see first? | An empty state in the tab with one brown **Add PAYE bands** button and outlined **Add a deduction**. Rate and band rows are sample-only in Paper. | Owner rule: the Accountant types and confirms. | None. |
| D24 | Names in the screen. **Owner.** | Always "Name, Role" (for example "Anne Muthoni, Accountant"), or the role alone. Paper's history uses "(Director)" in brackets in one place: build it as "Name, Role". No "he", "she", "her" or "his". | Owner follow-up of 19 Oct. | A copy change. |
| D25 | PIN. | The one PIN every signed act uses (`WorkforcePinDialog` field style, `PinField`). A wrong PIN keeps the dialog open with the PIN cleared. The server verifies the PIN in the same request and records the signature in the audit entry. | One kit, one check. | None. |
| D26 | Who may open Rules, and 404 versus 403. | See section 14 of the spec. Heads and floor staff do not hold `rules.read`: no menu link, the page answers 403. A Branch Manager asking for another site's id gets **404** (as built: do not confirm the site exists). Writing a field you may not change is **403** `RULE_FIELD_NOT_EDITABLE`. | Do not leak other sites. | None. |
| D27 | Version history length and filter. | 25 per page with the numbered pager and rows per page (the table convention). A **Site** select (Company rule, each site that has an own rule) is added beside the heading. | Table convention; the Branch Manager needs their own site's history. | Page size. |
| D28 | A row that sets two numbers (Shift-end prompt "10 min before · every 2 min"; Overtime multiplier; Reports "day 45 and day 80"). | One Change, one dialog with one NOW and NEW cell per number, one version. | Paper's one Change per row. | Split rows. |
| D29 | Conduct: "Notices already issued keep their old end date". | The notice stores `validUntil` when issued (Conduct slice); a rules change never rewrites it. Rules only gives the months for new notices from the date. | Owner's design copy. | None. |
| D30 | Where does the "Who edits what" table come from? | It is **generated by the server from the access table and the field policy** (`GET /workforce/rules/access-table`), so the screen cannot drift. The copy next to it is fixed text. A test fails if a tab has no row. | Paper step 13 is a table; two sources would disagree. | A hand-kept table. |
