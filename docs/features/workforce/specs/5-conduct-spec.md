## 3. The status machine of a notice

Stored fields: `status` (the headline) and facts `signedAt`, `notSignedRecordedAt`, `appealedAt`, `decidedAt`, `endedAt`. Level: VERBAL_NOTE, WRITTEN_WARNING, FINAL_WRITTEN_WARNING.

| Status (word shown) | Meaning | Reached by | Next | Active? |
|---|---|---|---|---|
| ISSUED ("Issued", staff "To sign") | Sent, no signature yet (Written or Final only) | issue | SIGNED, GIVEN_NOT_SIGNED, APPEALED, ENDED, WITHDRAWN | yes |
| RECORDED ("Recorded") | Verbal note on the file, no letter | issue (Verbal) | APPEALED, ENDED, WITHDRAWN | yes |
| SIGNED ("Signed") | The person confirmed receipt | sign | APPEALED, ENDED, WITHDRAWN | yes |
| GIVEN_NOT_SIGNED ("Given, not signed") | Refused, not reached, or no login, with a witness | not-signed | SIGNED (late), APPEALED, ENDED, WITHDRAWN | yes |
| APPEALED ("Appealed") | With HR (or the Director) | appeal | KEPT, REPLACED, WITHDRAWN | yes (stands until decided) |
| KEPT ("Kept on appeal") | Decision: stands | decision | ENDED, WITHDRAWN (HR change) | yes |
| REPLACED ("Replaced on appeal") | Reduced; a new notice exists | decision | none | no |
| WITHDRAWN ("Withdrawn") | Does not count; stays on the file with the reason | decision or HR change | none | no |
| ENDED ("Ended") | Past `validUntil` | daily job and read-time derivation | none | no |

An appeal can start from ISSUED, RECORDED, SIGNED or GIVEN_NOT_SIGNED while the days last. The `signedAt` and `notSignedRecordedAt` facts stay whatever the headline becomes. **Rules:** one appeal per notice and never on a notice created by a reduction; a replaced or withdrawn notice cannot be signed or appealed; an Ended notice is read-only and still readable by HR, the Director, the issuing site's manager and the person; **nothing is ever deleted** (no delete endpoint, no `DELETE` in the repository). Every transition writes a `ConductNoticeEvent` and an audit entry in the same transaction and is refused with `409 INVALID_TRANSITION` from any other status (a pure function `nextStatus` with a table test).

**Tables (migration plan, additive).** `conduct_notices` (id, `siteId` ("organization_id" column), personId, issuerId, level, about, number Int? unique from `conduct_notice_seq`, verifyCode, `letterVersion`, `letterSnapshot` jsonb, `factsSnapshot` jsonb, `ownLine`, issuedAt, `ackDays`, `appealDays`, `validUntil`, status, signedAt, notSignedRecordedAt, notSignedReason, witnessId, witnessConfirmedAt, appealedAt, appealReasonKey, appealText, decidedAt, decidedById, decisionOutcome, decisionReason, `replacesNoticeId`, `replacedById`, `documentVersion`, createdAt, idempotency key unique per issuer), `conduct_notice_events` (append-only: noticeId, at, kind, actorId, label, payload), `conduct_notice_seq`. All queries include `siteId` (the person's site at issue); a manager's scope also joins on the person's current site (C26). No change to `disciplinary_records`.

## 6. Expiry and escalation (C7, C21)

`validUntil` = issue date plus the level's months from the Rules version in force that day (calendar months, clamped to month end; 9 Oct plus 6 months is 9 Apr 2027) stored on the notice; a later Rules change never moves it (D29). Active through the `validUntil` day. The list's "Active" and the file's "Active" mean status in the active set above **and** today at or before `validUntil` (derived at read time); a job at 00:10 Nairobi sets the stored status to ENDED and writes the event, so the Ended chip and the counts agree with the derived reading. No message is sent when a notice ends (no noise). The suggestion `suggestLevel(activeNotices)` is in section S9 and counts only active, non-replaced, non-withdrawn notices; legacy rows never count. A reduction restarts the clock at the decision date for the new level (C17); the reduced written gets a fresh `appealDays` of **0** (no new appeal).

## 7. Documents (C18, C23, C24)

WRN numbering is a DB sequence issued at issue for Written and Final notices only (gaps allowed). The frozen snapshot is the document; PDFs are rendered on demand (and cached by `documentVersion` in the file store). **Versions:** v1 as issued, v2 the same plus the decision page, v3 only if HR changes the notice again; an earlier version is never overwritten. The QR carries `{origin}/verify/WRN-0007?c={verifyCode}`; Segment 6's verify page answers with number, level, issue date, site name and the current headline only. The signatures printed on the document are the issuer's (name and role, "Signed with PIN" and time) and the person's receipt (or the not-signed record), plus the decider's on a decision page. Retention 7 years (matches the audit log); nothing is purged by this segment.

## 8. What the server provides, in one place

Module `backend/src/modules/workforce/conduct/` with sub-modules `notices/` (issue, list, detail, sign, not-signed, witness), `appeals/` (appeal, decision, change), `letters/` (constants, render), `documents/` (PDF, QR), `rollout/` (the site guard and legacy read), `_shared/` (status machine, scope, events). Every route is `authenticate`, `attachWorkforceSubject`, `requireCapability(...)`, a Zod schema, a service that owns the rules, a repository that always filters on `siteId`, no new `requireRole` list. New access rows go into `workforce-access.ts` (section 12). Pure units with tests: `nextStatus`, `suggestLevel`, `validUntil`, `appealDeadline`, the letter fill, the facts selection.

## 9. Idempotency and two people at once

Issue, sign, not-signed, appeal and decision each carry an `idempotencyKey` (the page generates one per open dialog); the same key returns the first result. Status changes are compare-and-set on `status` (`UPDATE ... WHERE id = ? AND status IN (...)`): the loser gets 409 with the current status and the screen shows what happened. The notice number is issued inside the issue transaction (the audit write is the last write, per the audit rule). A witness confirm and the manager's second record race harmlessly.

## 10. Rules read from the Rules store (built)

`rules.conduct`: `levels[].validForMonths` (3, 6, 12), `acknowledgeWithinDays` (3), `appealWithinDays` (7). The service reads the version in force on the issue date, copies the three values onto the notice, and never rereads them. `requiresLetter` and `issuableBy` stay in the stored rule but are **not read by the screens** (the access table is the authority for who issues). `HR_DECISION_DAYS = 7` is a constant (C20).

## 13. Accessibility (all screens)

Each stepper is an ordered list with the current item `aria-current="step"`; states have text, never colour alone ("done", "current", "to come" as visually hidden text). The status tag reads "Status: Signed". Dialogs and the issue panel are modal with focus trapped and returned; Esc closes, never submits; Enter in a PIN field never sends. Errors are `role="alert"`; the slowed state `aria-live="polite"`. Tables are real tables; the selected row is `aria-selected`; chips are a labelled group with `aria-pressed`. Download squares and chevrons have names. Targets 44 px on the phone. Amber on white is `#8A5A16` (contrast 5.3 to 1). Dark header text meets 4.5 to 1. The A4 document has a real text layer (selectable, not an image) and the PDF is tagged where the library allows; the phone Document view has a text alternative "Read the letter as text" for screen readers (the snapshot text, same wording).
