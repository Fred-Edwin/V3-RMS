## 2. The shared Change dialog

**Purpose.** One dialog for every Change link: makes a new version from a date, shows what it would change, says who is told. Drawn in Paper steps 02, 08, Chapter 10 steps 19 and 20.

**Layout (all measured).** `KitDialog` 580 wide, padding 28 side, title 20/26/600 ("Change <thing>", for example "Change the grace period", "Change how long a written warning stays", "Change annual leave", "Change minimum cover · Pastry"). Then top to bottom:
1. **Old to new block** (`OldToNew`, grey `neutral-50` panel, 1 px border, padding 16): three cells. Cell NOW: mono label "NOW" 10/12, value Geist Mono 20/24 (the same unit text as the row: "5 min", "6 mo", "21 d", "2 of 4"); arrow "→" (14); cell NEW: label "NEW", a bordered input 120 wide, 40 high, ink border when focused (first field focused on open); cell FROM: label "FROM", `SingleDateField` showing "Mon 2 Nov 2026" with the calendar icon. A row that sets two numbers (D28) shows two NOW and NEW pairs stacked, one FROM.
2. **Helper line**: one sentence 12/16 `neutral-600` saying what changing means ("Only the months a written warning stays on the file change. The letter and the level name are fixed.").
3. **Applies to** (only Lateness, Overtime and minimum cover fields that a site may override, Director and System Admin view): two radio cards "Every site" and "One site" (kit `RadioCards`); "One site" reveals a site select. A Branch Manager sees no control; the line says "Nyeri Town only". Paper draws it on step 02 only.
4. **Why? (required, and recorded)**: `FormField`, single-line growing to 3 lines, 1 to 500 characters, counter appears at 400. Label 13/600.
5. **Impact rows** (`KeyValueRows`, label left grey, value right ink, ink hairline top): up to 3 rows from the server (D12) then **Becomes: Version 3, from 2 Nov 2026** (always last). Months already approved: "Not changed" is returned by the server when a version dated inside an approved month would otherwise matter (D11).
6. **Your PIN** (`PinField`, one wide field 40 high, dots; the last digit signs, Enter never signs, number pad on phone).
7. **Who is told** caption 12/16: "The 4 Branch Managers, HR and the Accountant are told, with old and new. The old value, the new value, the reason and your name are kept in the audit log." (D1 for pay fields: "…are told it changed. The values, the reason and your name are kept in the audit log.") Counts and roles come from the preview.
8. Footer: outlined **Cancel** (38 high), brown **Save as version 3** (the only brown button; 38 high). Right-aligned, gap 10.

**Interactions and states.**
- Opens from a row's Change; Escape closes and returns focus to that link; scrim `neutral-950` at 35%. Focus order: NEW, FROM, Applies to, Why, PIN, Cancel, Save.
- On open it fetches `POST .../versions/preview` with the current NEW (or the empty change): shows a short skeleton in the impact rows. On every change of NEW or FROM (debounced 400 ms) it asks again.
- **Save is disabled with the reason as text under the button** until: NEW differs from NOW ("Nothing to change yet"), the value is valid (error under the field), FROM is allowed, a reason is entered, the PIN is 4 digits, and the server says `canSave`. The reason text sits in the helper line colour 12/16.
- NEW errors are the schema's, in plain words, under the field in `error-fg`: "Use a whole number from 0 to 60", "Say after how many lates". The server's `RULE_NO_CHANGE` shows as "That is the same as today."
- FROM: earliest day is the later of today (Nairobi) and the latest stored version's date (D9); Statutory has its own rule (D3). Past days are disabled in the picker with the title "A rule cannot start in the past". Default per D10. Errors: `RULE_BACKDATED` "A rule cannot start in the past."; `RULE_FUTURE_VERSION_EXISTS` copy in D9.
- Wrong PIN (`403 PIN_INVALID`): the field turns red (kit `PinField` error), "That PIN is not right. Try again.", the PIN is cleared, the dialog stays. Too many tries: the platform's lock message.
- Saving: button "Saving…" and everything disabled; success closes the dialog, the tab refreshes, a quiet toast "Saved as version 3, from 2 Nov 2026" (no Undo: a version cannot be unmade, only withdrawn, D22).
- Stale (D8): amber callout in the dialog "Someone changed this rule a moment ago. Check the new value." NOW is replaced, NEW and Why are kept, the PIN is cleared.
- A pay field needing confirmation (D2): after the impact rows an amber note: "The Accountant must confirm the new multiplier. Until then the old one stays in use." If the signer holds the confirming capability, the note says "You confirm it with this PIN" and the server confirms in the same request (as built).
- Network failure on save: the dialog stays, error callout "Could not save. Nothing was changed. Try again." (the write is atomic).
- Narrow desktop (1100): dialog stays 580 and scrolls inside at height 90vh with the footer pinned. Phone is not a Rules surface; at under 640 px the dialog becomes full width with the footer pinned.

**Server (create a version).** `POST /workforce/rules/:group/versions`, capability: the field's edit capability (never a `requireRole`). Body: `{ siteId: string|null, effectiveFrom: 'YYYY-MM-DD', values (full group for the company, only the overridable fields for a site, or {} for "use the company rule again" D21), reason, pin, expectedVersion? }`. Returns `201 { version: RuleVersionView, notice, confirmed: scope[] }`. Rules: date today or later in Nairobi, not before the latest stored version of the scope, same date a higher number; no difference from what is in force on that date → `409 RULE_NO_CHANGE`; validation in the group's Zod schema; every changed field needs its edit capability and a branch holder only their own site's override; pay fields' confirmations carried forward or given by the editor if they hold the confirm capability. Audit: `rules.version_created` in the same transaction (`RULES_PAY` for pay fields, `RULES_OPERATING` otherwise) with before and after, reason, the PIN signature. `POST .../versions/preview` takes the same body without reason and pin and returns `{ canSave, errors[], changedFields[], becomes: {version, from}, impact: {label, value}[], told: {role, count}[], needsConfirmation: {scope, whoCan}[], approvedMonthsAffected: false }`, no side effects.

**What production adds** (beyond Paper): loading, wrong PIN, stale, date errors, disabled-with-reason Save, network failure, narrow widths, the Applies to control on fields only some tabs have, focus order and Escape, a preview call so the impact rows are real.

## 3. The locked Change popover and "Fixed"

**Paper.** Holidays step 10: a Change link with a padlock icon (grey), a card under the row (300 wide, 12/16 padding, 1 px `neutral-200`, shadow `0 4px 14px #17151214`) with title "You can read this but not change it" (13/16/600) and the text "Only the Accountant can change the holiday pay rate. Ask the Accountant." Leave step 18: locked links on minimum cover rows, text "Only the Branch Manager of Nyeri Town, the Director or the System Admin can change minimum cover. Ask one of them." Rows the system sets say **Fixed** in the same slot (Probation signed contract, Casual who records and who approves, Week unpaid break).

**Spec.**
- A locked Change is a **button** (not a link to nowhere): padlock 12 px then "Change" in grey; it opens the popover on click, Enter and Space. It is never `disabled` (disabled controls cannot be focused or read). `aria-haspopup="dialog"`, `aria-expanded`, the popover is `role="dialog"` with `aria-labelledby` the title; Escape closes and returns focus to the button; clicking elsewhere closes it. Only one open at a time.
- Popover text is generated: `Only {list} can change {thing}. Ask {one of them | the X}.` The list comes from the row's `lockedReason.whoCan` (`{role, siteName?}`): joined "A, B or C"; a Branch Manager entry reads "the Branch Manager of {siteName}" for a branch holder of that site; "the Director", "the Accountant", "HR", "the System Admin". One entry: "Ask the Accountant." Two or more: "Ask one of them." The thing comes from a fixed per-row noun in the front-end copy file.
- If nobody can change it (a Fixed row) there is no padlock: the slot says **Fixed** (not a button); a one-line help carries the reason (already in each row's help).
- Popover width 300, placed under the row, right-aligned to the slot; flips above near the bottom. On narrow screens it spans the panel width.
- Role-blind for an Accountant on a Director row and so on: the padlock appears wherever `canChange` is false and `kind` is `EDITABLE`.
- Never shows a role the viewer cannot name; never shows a person's name (D24).

**Server (the answer behind the padlock).** For each row the page response (section 1) carries `canChange` and `lockedReason.whoCan`, computed from the access table and the field policy for the viewer **and the scope** (a Branch Manager of another site: whoCan includes "the Branch Manager of Nyeri Town"; a Director: empty list means Fixed). No separate call per click.

## 17. How a change takes effect

- **Versions are never edited or deleted** (a static test already checks the repository). A change inserts a `RuleVersion` with the **full** new values, an effective date and a required reason; confirmations and withdrawals are rows too.
- **Effective date.** Today (Nairobi) or later; not before the latest stored version of the scope; the same date makes a higher version number. Statutory alone may start on a past day, never inside an approved month (D3). The rule is read **by the date of the day it applies to**: payroll and attendance resolve `getEffectiveRules(siteId, date)`. A version starts at **00:00 Nairobi** of its date.
- **Site override.** Resolved as the company version at the date, then the site override's fields laid over it; an empty override follows the company rule (D21).
- **Pay fields** (D2): until confirmed the old confirmed value stays in use; once confirmed the new value applies from its own date to every month not yet approved.
- **An approved month never changes** (D11): approval freezes the month's rule values; a later version dated inside it saves but the dialog says "Not changed". A paid month is the same. This depends on the 1A month snapshot; until it ships the server refuses nothing here but the preview says "Not changed" and Statutory refuses dates before the open month.
- **Past data.** Leave already taken or booked, conduct notices already issued, rota already published, clock events already recorded: never recounted (stated in the relevant dialogs).
- **Two people at once:** D8. **Withdrawal:** D22.
- **Time maths** goes through `_shared/time` Nairobi helpers only, never server-local time.
