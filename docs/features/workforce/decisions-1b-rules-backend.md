# Workforce segment 1B (Rules): back-end decisions

19 October 2026, branch `feat/workforce-1b-rules-backend`. Choices taken while building the back end of the Rules screens, beyond or against `specs/1b-rules-spec.md` and `specs/decisions-1b-spec.md` (D1 to D30). Each row: the question, what was built, why, and what changing it takes. "Departure" marks a place where the build differs from the spec text.

| # | Question | Choice | Why | What changing it takes |
|---|---|---|---|---|
| B1 | What does `values` mean in a save? (Spec: full group for the company.) | **Addition.** Company scope: the rows to set, laid over what is in force; a full group works too. | A dialog changing one row should not have to resend (and so overwrite) the other rows. | Require a full group in `plan-input.ts` `companyChange`. |
| B2 | How does a site own part of a tab? (Spec: "only the overridable fields".) | **Departure in detail.** A site version stores any subset of its rows; site schemas are `partial()`. The merged result is validated as a whole group. | Overtime "per row that has an own rule" and "company rule now says X, the site keeps its own" need per-row ownership. The slice-0 test that demanded every site field was rewritten. | Make the site schemas total again; every site row becomes frozen. |
| B3 | Site save semantics. | Own rows = existing own rows plus `values`, minus `useCompanyRuleFor`; an empty body hands every row back (D21). | One body covers "make mine", "give this row back" and "give all back". | Drop `useCompanyRuleFor`. |
| B4 | Unknown names in `values`. | Refused, `400 RULE_FIELD_UNKNOWN`; unknown body keys are a Zod 400 (`.strict()`). | A typo must not be silently dropped. | Remove `rejectUnknown`. |
| B5 | Fixed and derived rows. | Policy `edit: null` = Fixed (rounding, the casual lateness switch, `timesheetPeriod`, `timesheetCutoff`); `derived` = computed (`enabled`). A changed Fixed row is `403 RULE_FIELD_NOT_EDITABLE`; a derived row is never listed as changed and needs no right. | Spec section 6 and D14. | Give the field an editor in `rules-field-policy.ts`. |
| B6 | Stale check (D8). | `expectedVersion` is the highest number in the scope, and the page returns it as `expectedVersion` (company) and `expectedSiteVersion`. Checked in the pre-flight and again under the lock. **Departure:** the spec says "the version the screen showed"; that would be stale whenever a scheduled version exists. | Withdrawn numbers count too, since numbers are never reused. | Compare with the in-force number instead. |
| B7 | Two saves at once. | Advisory transaction lock per (company, group, site); the plan is made again under it. A retry with the same `idempotencyKey` (body or `Idempotency-Key` header) answers `200` with the first result; the key is a nullable unique column. | Real concurrency safety and double-click safety. The database test caught a Prisma `void` bug in the lock call. | Drop the column and the lock. |
| B8 | Order of refusals. | Everything the person can fix first (rights, dates, values, no-change, stale), then the PIN, then the write. A fixable mistake never counts as a wrong PIN. | Locking someone out for a date typo would be cruel. | Move `verifySignerPin` first. |
| B9 | PIN (D25, gap 2). | New `_shared/pin/signer-pin.ts`. Wrong: `403 PIN_INVALID` (not 401: the apps treat 401 as logged out). None set: `403 PIN_NOT_SET`. Five wrong in ten minutes: `429 PIN_LOCKED`, counted per process. **No PIN expiry exists on the platform, so none is checked.** | The Timesheets check (`401 INVALID_PIN`) would log the screen out. A shared lock needs a platform table. | Move the counter to Redis or the database. |
| B10 | Audit of the signature. | `after.signature = { method: 'PIN', signedAt }`; the PIN is never stored, logged or returned. A test searches the entry. | Same as the Timesheets report signature. | None. |
| B11 | Notice content (D1). | Event `rules.version_created` carries `pay` and `changes[]`: old and new for ordinary rows, **empty when any pay row changed**. The HTTP reply carries counts per role (`notice.told`), not people. | No figures on a lock screen; no staff ids sent to a screen that does not need them. | Return `recipients`. |
| B12 | Who is told. | The TOLD column of the spec table, in `plan-notice.ts`. Additions: a site's own rule tells that site's manager instead of all; minimum cover tells the site's department heads instead of all managers; a Branch Manager's change also tells the Director; a pending confirmation tells the Accountant (the Director for the holiday list). New audiences `HR`, `ACCOUNTANT`, `DEPARTMENT_HEADS`. | Spec sections 16 and 18. Heads come from the department-head rows. | Edit the table. |
| B13 | Approved months (D11). | Interface `ApprovedMonthGuard` in `plan/plan-months.ts`; the safe default treats every month before the current Nairobi month as approved. Statutory cannot start earlier than the 1st of this month; the preview always says "Not changed". The Timesheets month-approval status is not merged. | The brief allows a small interface with a safe default. | The real status calls `setApprovedMonthGuard` once. |
| B14 | Other tabs "inside an approved month". | Because only today or later is allowed, only the current month can be affected. A version still saves and applies from its day; payroll must read the approved month's snapshot (D11). **The back end cannot enforce this alone** until the snapshot exists; `approvedMonthsAffected` is the hook. | The resolver answers by date and cannot know a month is frozen. | Payroll/Timesheets slice. |
| B15 | Withdrawal (D22). | Only the newest live version of its scope, only before its day, a reason and PIN, idempotent. **Addition:** "newest only" (`RULE_VERSION_NOT_LATEST`). | Later versions hold full copies of earlier values; withdrawing the middle one would leave a contradictory timeline. | Allow any and re-check later ones. |
| B16 | Confirmation (gap 5, D2). | `POST /versions/:id/confirm`, capability from the scope, PIN, idempotent, refuses a withdrawn version and a site version. A pay row resolves to the newest *confirmed* version; the page lists `pendingConfirmations` with the version id for the Confirm button. `missingConfirmations` now means "no confirmed value at all". | D2 and the Overtime callout. | The resolver in `rules-resolve.ts`. |
| B17 | Statutory (D3, D23, gap 11). | Ships empty. Bands must start at 0, follow with no gap and no overlap, only the last open-ended, each with a rate (0 to 100) or a flat amount; a deduction appears once. Past start only from the first open month. `appliesFrom` per table is **not** built; the history gives `changedSummary` ("NSSF 6% (was 5%)"), figures only for `payrun.read` holders. | Contiguity is the invariant payroll needs. A derived `appliesFrom` can be computed from the history on the screen. | Add to the page response. |
| B18 | Schema additions (gap 7). | Overtime `{ordinaryDay, restDay}` (1 to 5); casual rates by `departmentId` (1 to 100,000, one each); probation `reminderDaysBeforeEnd` and `reportDays`; leave-type columns; holidays one per date, rate 1 to 5. Older stored values read through defaults or a `preprocess`; **no SQL data migration**. | Nothing real was ever stored (no write path existed). | None. |
| B19 | Access fixes (D4 to D6, gap 3). | `rules.edit.leave` split into `leave_types` (HR) and `min_cover` (unit managers, Director, System Admin); new `holiday_pay` (Accountant); `holidays` moved from HR to the Director; the System Admin lost lateness, overtime and attendance. Cell tests added to `workforce-access.test.ts` and the matrix updated. | Spec section 14. | The access table. |
| B20 | A Branch Manager naming another site. | Reads: `404 Site not found` (the spec's rule; the old service answered 403). Writes: `403 RULE_FIELD_NOT_EDITABLE`. | Spec section 14, with its two rules both kept. | Make writes 404 too. |
| B21 | "Who can change this row". | Computed per row in the page response from the access table and field policy for the viewed site; no call per click. A Fixed row, or a row nobody can change, has no padlock. | Spec section 3. | None. |
| B22 | Who edits what (D30). | `GET /access-table` generates ten rows with structured parts and one-line wording (`all but the deduction cap`, `Branch Manager for own site`). The row catalogue (`access-catalogue.ts`) is checked: every stored field is in exactly one row. | A new field cannot be left without an answer. | The catalogue file. |
| B23 | Impact rows (D12). | Only statements the server can stand behind (conduct notices keep their end date, past leave not recounted, published rotas unchanged, "Months already approved: Not changed"). **Counts that need other modules (late marks, requests waiting, people on probation) are left out, never invented.** | The brief: computed or omitted. | Add functions in `plan-impact.ts` once those modules can answer. |
| B24 | History. | Paged (10, 25, 50, 100), status (`SCHEDULED`, `IN_FORCE`, `REPLACED`, `WITHDRAWN`), who is told, "what changed" in words, withdrawn by and why, a Site select list (a Branch Manager sees only their own site), and `canWithdraw` for the viewer. **Departure:** the old reply was a bare array; it is now a page object. "Pay read" for figures in the words is `payrun.read`. | Spec section 15 and D27. | None. |
| B25 | Start-day window. | The preview returns `earliestEffectiveFrom` and `defaultEffectiveFrom`; a week-start change must start on the new first day (`RULE_DATE_NOT_WEEK_START`); at most 730 days ahead (`RULE_DATE_TOO_FAR`). **Additions.** | Stops a typo from sitting in the timeline for ever. | `MAX_DAYS_AHEAD`. |
| B26 | Conduct body. | The screen may send `levels: [{ level, validForMonths }]`; label, letter and issuers are carried. | Spec section 10. | `mergeConductLevels`. |
| B27 | Folder shape. | The 14-file `rules/` folder was split into sub-folders with `git mv`. `rules-service.ts` stays as a three-export shim and `index.ts` is the public face, so the ~25 other Workforce files did not change. | Merge safety with the other lanes. | None. |
| B28 | Test support in `src`. | `rules/testing/rules-fake.ts` ships in the build (the repo has no separate test-support folder). | One in-memory stand-in for ten test files. | Move when a convention exists. |
| B29 | Proof users. | The lane data has no waiter; the Store Attendant (same access row as a waiter) stood in. The lane Director, Branch Manager, HR, Accountant, Store Manager, System Admin and a kitchen head were real logins. The proof added `Proof:` versions, then removed them; their audit entries stay (append-only). | Honest note. | None. |
