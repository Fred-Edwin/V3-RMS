## 2. The method (do not reinvent it)
The method is written down: **`docs/FEATURE_REDO_PLAYBOOK.md`** (rewritten 20 Oct 2026, on `main` since PR #148) and five reusable briefs in **`docs/process/templates/`** (orchestrator start, segment review, spec session, back end, front end). Read the playbook once; its sections §5 (pipeline), §8 (lanes and stacked branches), §9 (code rules), §11 (which docs live how long) and §13 (learnings) matter most. In one line: **plan, Paper designs approved by the owner, segment review, spec session, back-end session, front-end session, one merge per segment, the owner walks it and approves.**

The owner's standing rules (put them in every brief; they are in the templates):
1. **Paper is a demonstration; production is the goal.** Agents add whatever real use needs that Paper does not show and log it.
2. **Decide by default using your recommendation, log it** (*question, choice, why, what changing it takes*); ask the owner only when you cannot trust your recommendation or the choice is expensive to reverse.
3. Sessions open their final message with the **decisions table**, then a **5-line plain-English recap**.
4. **Front ends: assemble from the kit, one Paper screenshot per screen**, never per-component or per-dialog audits; no automated pixel-diff, ever.
5. **Keep code tidy as it is built:** files at most 350 lines (aim 250), folders at most 12 files, no catch-all `utils`, an `index.ts` door per module, thin `app/` pages, layers separated.
6. **No gate left red, lint included.** Sessions edit with the Edit and Write tools only, with a `Why:` line before each; no `sed`, `awk`, heredocs or `cp` for editing; no subagents; read only what the brief names.
7. Nothing is pushed or merged to `main` by build sessions. **You push branches to GitHub as a backup at every hand-off** (a branch push never deploys). **Never merge to `main` or open a PR without the owner's explicit word.**

## 7. The orchestrator's routine for each report the owner pastes
1. Read the report; say plainly what was done, what you accept, and any slip (missing `Why:` lines, a heredoc edit, an unrun check). Do not make the owner wait or re-verify what the session proved; check the lane is clean (`git status`), the branch name, and that the owner's approval is recorded.
2. **Push the branch as a backup** (`git push -q -u origin <branch>`).
3. **Merge lines that belong together** in a new stack branch cut from the previous top (`git checkout -b <new> <branch-a>; git merge --no-edit <branch-b>`). Typical conflicts: the access table, capabilities list, audit actions, nav rows and the nav test, the time-zone script in `backend/package.json` (append folders), status docs, `API_CONTRACT.md` (renumber a clashing section). Resolution technique that works: for a doc with both sides editing the same rows, `git checkout --ours <file>` then re-add the other side's content with Edit; **the Edit tool needs a Read of the file first**.
4. **Verify the merged code:** `pnpm exec prisma generate`, backend `pnpm exec tsc --noEmit` and the affected tests, front end `pnpm exec tsc --noEmit`, `pnpm exec eslint features/workforce components/app/shell lib` (must be 0 errors) and the affected vitest folders, and `pnpm build` before telling the owner it is clean.
5. **Update docs in the same pass:** the status row in `docs/PROJECT_STATUS.md`, the Workforce README slice table, `ROADMAP.md`; record the owner's approvals when they say so.
6. **Write the next brief** from the template, commit it on the stack, push, then give the owner the lane commands and the prompt to paste (they paste a one-line prompt: "Read docs/sessions/<file>.md in full and do exactly what it says...").
7. Keep the answer short: a plain-words review, a table, the exact commands, what to expect, and what you need from the owner.

## 8. Gotchas learned (save yourself the time)
- A brief committed on one lane's branch is invisible to a lane on another branch: **commit briefs on the stack and cut lanes from it.**
- zsh fails on `grep --include=*.ts` ("no matches found"); run grep without the flag. The `Grep` tool is not available: use `grep` through Bash. Do not write the memory path with a slash instead of a dash.
- Paper MCP: call `get_guide` once, **never `get_basic_info`** (huge token list); use node ids directly; `find_nodes` by text works within a node. Do not edit Paper unless the owner asks; record inconsistencies in the spec.
- Sessions regularly: skip a `Why:` line, use `sed` or `cp` once, run `prisma format` on unrelated files, overwrite PIN backups in a lane database (fixed: the proof script never overwrites a backup now), or leave a lane site switched on. Say it loudly in every brief; check the lane after each session.
- `git worktree` forbids the same branch checked out in two lanes; cut a new branch from it instead. `git branch -D` is needed for squash-merged branches. `gh pr merge` without `--delete-branch` from a worktree.
- The Prisma client must be regenerated in a lane after a merge brings new tables (`pnpm exec prisma generate`), or `tsc` shows false errors.
- Lane PIN, proof scripts and demo seeds change data in the lane database only; never touch production data or the owner's main database.
