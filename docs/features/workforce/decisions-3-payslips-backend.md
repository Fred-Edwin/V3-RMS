## Decisions

| # | Question | Choice | Why | What changing it takes |
|---|---|---|---|---|
| S1 | The spec says a wrong code and a missing unlock answer `401`. | `403` with codes `CODE_WRONG` and `UNLOCK_REQUIRED`; `429 CODE_SLOWED` for the pause. | The apps treat a 401 as "signed out" (the signing PIN already answers 403 for the same reason). A wrong code must never sign anyone out. | Change the status in `unlock-service.ts` and `unlock-middleware.ts`. |
| S2 | Relock after 60 seconds in the background (PD2). | The server enforces the 10 minute idle rule and a hard cap of 8 hours, and `POST /me/lock` ends an unlock at once. The 60 second background rule is the phone's job: it calls Lock when the app goes to the background for 60 seconds or the person leaves My payslips. | The server cannot see a backgrounded page. | Constants in `unlock-rules.ts`. |
| S3 | Unconfirmed phones (PD4) while "Is this your phone?" does not exist. | A hook `setDeviceConfirmationSource`. The default says "unknown": audit records `confirmed: false`, nobody is paged. When the feature registers `false` for a phone, the person and the System Admin get the loud notice. | Spec section 15 says the System Admin push is held back until the feature ships. | Register the real source at start-up. |
| S4 | Does a wrong try during the pause count? | No. A try answered `CODE_SLOWED` is not recorded as a try and not checked, so the pause cannot be used to extend itself. The right code still opens once the pause is over (nobody is locked out). A right code ends the count. | Keeps the count honest and never locks anyone. | `unlock-service.ts`. |
| S5 | One writer at a time per person. | A Postgres advisory lock on the person around each try. | Two phones guessing together could pass the 3rd/5th try checks or both raise the alert. | n/a |
| S6 | First code (`POST /me/code`). | Also returns an unlock token, so "Save my code" opens the payslips with no second call. HR's existing reset (`staffService.resetPin`) clears the PIN, which the unlock reads as "no code"; the reset itself is not audited here because that is People's action. `payslip.code_reset` was therefore not registered. | One round trip; no dead audit code. | Register the action and call the writer from the reset. |
| S7 | Which payslips are visible to staff before Payroll part 2 exists. | A publication seam (`reads/publication.ts`): visible once the month state is `PUBLISHED` or later (compared as text). Pay day and paid date come from the seam and are `null` by default. | See "Assumptions about Payroll part 2" below. | Register the real source. |
| S8 | Stable payslip id. | The id of the version-1 row is the payslip's id for ever; `?v=2` selects a version. Any version's row id also resolves to the same payslip. | The route `/payslips/[id]?v=` must not change when a correction arrives. | n/a |
| S9 | Only the current run counts. | A payslip row from an older calculation of a month is a 404. | A recalculation before approval must never surface. | n/a |
| S10 | Who opens anyone's payslip (`payslip.read_any`). | A new capability for HR and the Accountant. The Director is the audience (digest), not an opener. Only published payslips can be opened; an unpublished one is a 404. The Payroll page's own `payroll.read` detail is unchanged and unaudited (part 1). | The spec's `payrun.read` is gone; `payroll.read` is held by the System Admin, who must not open payslips. | Table row. |
| S11 | Director's "one row per opener per day" (PD5). | A digest table counts openings per opener per day; the Director is told on the first opening of the day by each opener; `GET /payslips/opens?day=` gives the running count (capability `audit.read.payslip_access`). The notification system has no "update a row", so the count lives on the digest. | Stops a flood; the count is always right. | Notification slice can update its row from the digest. |
| S12 | Stored A4 payslip (PD16). | Drawn once, from the frozen lines, stored in `payslip_documents` (insert-only trigger) with its hash; every view, download and share is those bytes. A replaced version is drawn once more as REPLACED (watermark, "Replaced by version 2 on ..."); the original file stays. Part 2 may call `ensureFileForPayslip(id)` at publish and at each correction; until then the first read makes it. | Byte-identical downloads without waiting for part 2. | Call the door from part 2. |
| S13 | Leave balance box and the employer KRA PIN on the payslip. | Left out. Leave balances do not exist (slice 5) and no employer KRA PIN is stored anywhere. | No invented data on a legal document. | Add the fields to the draw code when the data exists. |
| S14 | P9 layout "kept with the Statutory tables". | A versioned layout file (`p9/p9-layout.ts`, columns by key and label, structure only). The Accountant's confirmation is stored per layout version; a new version needs a new confirmation. No tax rule is in the P9 code: every figure is read from the frozen payslip (gross, taxable pay and PAYE are the payslip's; contributions = taxable earnings less taxable pay; tax charged = the income tax line's bands added; relief = tax charged less PAYE). A payslip whose tax line has no bands shows tax charged equal to PAYE and no relief. | Putting the layout in the Rules store needs its own versioning, tab and screen. | Move the constant into a Statutory row. |
| S15 | P9 build rules. | Built once per person, year and layout version under a lock, stored with its hash and the twelve rows. A missing KRA PIN (409 `P9_NO_KRA_PIN`, HR told) or a month of the employment with no payslip (409 `P9_MONTH_MISSING`) stops it. A leaver's card is available from the day their final month is Paid; HR builds it with `POST /p9/:year/people/:employeeId/generate`, which returns the PDF. | PD13, S12 of the spec. | `p9-rules.ts`. |
| S16 | Old payslip card (PD12). | `legacy: { onNewSystem, hasOldPayslips, card, historyRow, emptyReason }` on the list, home and history. Old payslips are those the old system published (`is_locked`). | One shape for all three screens. | `legacy-card.ts`. |
| S17 | HR contact (PD11). | `LEAVE.hrContact {phone, hoursText}` or `null`, edited in the same Rules row as the leave types (HR only). | Keeps the existing "who edits what" wording. | Rules schema. |
| S18 | Casual: how the sheet is found when the phone has no signal. | `PUT /casuals/sheets/lines` finds or creates the sheet by site, department and date (the spec's `PUT /sheets/:id/lines` needs an id the phone does not have yet). The request carries `version` and an `idempotencyKey`: the same key returns the first result; a stale version is 409 `CHANGED_UNDERNEATH`. Query names are `siteId` and `departmentId`. | Offline-safe creation. | Routes file. |
| S19 | Day pay (PD22). | `rate x minutes / 480`, rounded half up to the whole shilling, in integer cents. "Up to 8 hours at rate x hours / 8, over 8 at an eighth each" is one straight line. A 9 hour day at 900 pays 1,013 (1,012.50 rounds up). | Exactly the spec; one formula. | `casual-pay.ts`. |
| S20 | Overlap check across midnight and sites. | A shift can end past midnight (`endsNextDay`, shown as +1). Overlap is checked on absolute minutes against the worker's shifts on the day before, the day and the day after, on any site, under a per-worker advisory lock so two heads cannot both record the hours. The message names the site and times, never the other head. | PD23; races. | `shift-rules.ts`. |
| S21 | Who approves a manager-recorded sheet. | A sheet a Branch or Store Manager recorded is decided by the Director only (403 `DIRECTOR_ONLY` for another manager); nobody decides a sheet they recorded or sent (403 `SELF_APPROVAL`). The Director may also decide the Director's own site. | PD24 says it is sent to the Director. | `approval-rules.ts`. |
| S22 | Frozen casual sheet. | At approval one transaction numbers the sheet (CPS-n from a locked counter; gaps allowed), stores the snapshot and its SHA-256, the cash holder (the Rules' named person, else the approving manager, else the site's manager) and audits. It is not stored as a file. | Same evidence value, no extra table. | Add a stored-file table. |
| S23 | Rate changed between send and approval. | The sheet is re-priced and the call answers 409 `RATE_CHANGED`; the screen re-reads. | PD16, S8 of the spec. | `recording-service.ts`. |

## Assumptions about Payroll part 2 (lane 1), and where each lives

1. **Published, paid, pay day, paid date** are read through `payslips/reads/publication.ts` (`setPublicationSource`). The default treats a month as published when its state text is `PUBLISHED` or `PAID`; it returns no pay day and no paid date. Part 2 should register a source reading its own columns (or its states plus pay day and paid date). Until then the P9 treats a Paid December with no date as paid from 1 January.
2. **Payslip rows**: version 2 is another `payroll_payslips` row in the month's current run with `version = 2`, `correctedAt`, `correctedById` and the same `documentNumber` as version 1. Staff reads, the "corrected from" marks and the A4 file work from that. The `diff` and `reason` columns are not read.
3. **PS- numbers** are read from `payroll_payslips.document_number`. If it is null the document shows "Payslip" and the file name has no number.
4. **Signer** of version 1 is the month's `approved_by_id` and `approved_at` (the Accountant's approval, PD18); of version 2 the payslip's `corrected_by_id` and `corrected_at`.
5. **A4 files**: part 2 may call `ensureFileForPayslip(payslipId)` at publish and at each correction. Nothing breaks if it does not.
6. **Notices**: `payslip.published` and `payslip.corrected` are part 2's to send (it publishes and corrects). This segment sends the code, opening, casual and P9 notices only. Kinds used: `payslip.three_wrong_codes`, `payslip.on_unconfirmed_phone`, `payslip.opened_by_staff`, `casual.sent`, `casual.approved`, `casual.sent_back`, `casual.voided`, `casual.to_pay`, `p9.no_kra_pin`. Wording rows live in the front end's `notification-copy.ts`; none of the data carries a pay figure.
7. **Casual tab**: part 1's `casualPay` still returns zeros. Wire it with one line: `return { ...(await casualMonthSummary(companyId, monthKey)), state: month.state };`.

## Gaps the front-end session must know

- Send the phone's random id in `x-device-id` on every payslip read and the token in `x-payslip-unlock`; call Lock when the app is backgrounded for 60 seconds.
- `UNLOCK_REQUIRED` and `CODE_WRONG` are 403, not 401 (S1). `CODE_WRONG` may carry `details.waitSeconds`.
- The list (`/payslips/me`) carries no amounts and needs no token; everything else does.
- Notification wording rows for the kinds above; "pay run published/reopened" rows are Payroll's.
- The nav rows and `capabilities.ts` copy in the front end need the three new capabilities.
- No employer KRA PIN and no leave balance on the A4 payslip (S13); the P9 needs the Accountant's one-time confirmation before anyone can download.
- A department head's phone sends `date` as the Nairobi calendar day; the sheet's `endsNextDay` marks a shift past midnight.
- The Payroll page's "open payslip" link for HR is `GET /workforce/payslips/:id` (and `/document`), audited.
