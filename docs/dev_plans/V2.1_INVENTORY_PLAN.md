## What V2.1 Builds

End-to-end inventory tracking across the Central Kitchen and all branches:

1. **Supplier deliveries** — Store Manager logs incoming raw ingredients
2. **Conversion table** — Director maps menu items to ingredient quantities
3. **Morning requisition** — Branch Manager requests portions by 6:00 AM
4. **CK dispatch** — Store Manager reviews, calculates capacity, dispatches
5. **Branch receipt** — Branch Manager confirms what arrived, flags discrepancies
6. **Automatic stock depletion** — PrepTicket READY event deducts branch stock
7. **Low-stock alerts and auto-hide** — System alerts and hides at thresholds
8. **End-of-day stocktake** — Branch Manager counts all three stations
9. **Management dashboard** — Director and Store Manager see everything

### Step 4 — Services

**New file:** `backend/src/services/inventory-service.ts`

All business logic lives here. No Prisma calls — use the repository.

Functions to implement:

**`createSupplier(data)`** — pass through to repository

**`getIngredients()`** — return with computed `canFulfilQty` if requested

**`logDelivery(data, loggedById)`** — create delivery record AND increment ingredient stock inside `prisma.$transaction`

**`createRequisition(organizationId, submittedById, data)`:**
- Enforce 6:00 AM cutoff: if `!data.isMidDay && currentHour >= 6` → throw `AppError('Morning requisitions must be submitted before 6:00 AM', 400, 'REQUISITION_CUTOFF')`
- Create requisition via repository

**`getRequisitionWithCapacity(id)`:**
- Fetch requisition from repository
- For each item, compute `canFulfilQty`:
  ```
  canFulfilQty = min over all ingredient conversions:
    floor(ingredient.currentStockCk / conversion.quantityPerPortion)
  ```
- Return requisition with `canFulfilQty` added to each item

**`dispatchRequisition(id, items, dispatchedById)`:**
- Validate all dispatched quantities are ≤ `canFulfilQty` (re-check inside transaction)
- Inside `prisma.$transaction`:
  1. Call `repository.dispatchRequisition(id, items, tx)`
  2. For each item dispatched, fetch all `IngredientConversion` for the `menuItemId` and call `decrementIngredientStock(ingredientId, qty * quantityPerPortion, tx)` for each
- After transaction: send FCM push to the branch manager (look up `organizationId` from requisition, find users with role `MANAGER` in that org, call `fcmService.send()`)

**`receiveRequisition(id, items, receivedById)`:**
- Inside `prisma.$transaction`:
  1. Call `repository.receiveRequisition(id, items, tx)`
  2. For each item received, call `incrementBranchStock(organizationId, menuItemId, receivedQty, tx)`
  3. For any item where `receivedQty < dispatchedQty`: record discrepancy (set a flag on `RequisitionItem` — add `hasDiscrepancy Boolean @default(false)` to schema if not already there)
  4. If previously hidden (`BranchMenuItem.isAvailable = false`) and now has stock → set `isAvailable = true`
- After transaction: if discrepancies exist, send FCM push to Store Manager

**`deductStockForPrepTicket(organizationId, menuItemId, qty)`:**
- This is called from `prepTicketService.markReady()` — not from an HTTP handler
- Must accept a Prisma transaction client `tx` — it will be called inside an existing transaction
- Decrements `BranchStock.currentQty`
- If `currentQty === 0` after decrement: set `BranchMenuItem.isAvailable = false`
- Returns `{ newQty, isLowStock, isOutOfStock }` so the caller can emit the right Socket.io events

**`submitStocktake(organizationId, conductedById, data)`:**
- Validate each entry has exactly one of `menuItemId` or `consumableId`
- Compute `variance = actualQty - expectedQty` for each entry
- Create `StocktakeSession` + all `StocktakeEntry` records in one `prisma.$transaction`

**`getInventoryOverview()`:**
- Aggregate across all active branches: today's requisition status, discrepancy count, total shrinkage from latest stocktake
- Include CK raw stock levels and items below reorder threshold

### Step 5 — Modify `prepTicketService.markReady()`

**File to edit:** `backend/src/services/prep-ticket-service.ts`

This is the only modification to existing V1 code. It is additive — the existing logic is unchanged; stock deduction is added inside the same transaction.

Find the `markReady` function. It currently does something like:
```typescript
await prisma.prepTicket.update({ where: { id }, data: { status: 'READY', readyAt: new Date() } })
```

Extend it to run inside a `prisma.$transaction` and call `inventoryService.deductStockForPrepTicket()`:

```typescript
const result = await prisma.$transaction(async (tx) => {
  const ticket = await tx.prepTicket.update({
    where: { id },
    data: { status: 'READY', readyAt: new Date() },
    include: { order: { include: { items: true } } }
  })

  // Deduct stock for each order item on this ticket
  for (const orderItem of ticket.order.items) {
    const stockResult = await inventoryService.deductStockForPrepTicket(
      ticket.organizationId,
      orderItem.menuItemId,
      orderItem.quantity,
      tx
    )
    // stockResult carries { newQty, isLowStock, isOutOfStock }
    // store these to emit socket events after transaction commits
  }

  return { ticket, stockResults }
})

// Emit socket events AFTER the transaction has committed
for (const { menuItemId, newQty, isLowStock, isOutOfStock } of result.stockResults) {
  if (isOutOfStock) {
    io.to(organizationRoom).emit('inventory:out_of_stock', { organizationId, menuItemId })
  } else if (isLowStock) {
    io.to(organizationRoom).emit('inventory:low_stock', { organizationId, menuItemId, currentQty: newQty })
  }
}
```

**Important:** Socket.io events must be emitted after the transaction commits, not inside it. The transaction is not committed until after all operations succeed — emitting inside it would notify clients before the data change is persisted.

**If `BranchStock` row does not exist for a menu item** (e.g. inventory tracking not yet set up for that item): log a warning and continue — do not throw. V1 orders must continue to work even before inventory is fully configured.

#### UI/UX Standard — Non-Negotiable

Every screen built in this step must conform to `docs/DESIGN_SYSTEM.md` without exception. Read it in full before writing a single component. The summary below is a checklist — it does not replace reading the source document.

**This is a premium product. Generic SaaS styling is a failure condition.**

**Colours — use only the defined palette:**
- Background: `bg-crema` (`#F5F0E8`) — never `bg-white` or `bg-gray-*`
- Cards/modals: `bg-parchment` (`#EDE7DC`)
- Primary action buttons: `bg-espresso` (`#2C1810`) text white — only where action is required
- Primary text: `text-stone-900` (`#1C1917`) — never pure black
- Secondary text: `text-stone-700` (`#44403C`)
- Muted text (timestamps, captions): `text-stone-500` (`#78716C`)
- Dividers/borders: `border-stone-300` (`#D6D3D1`)
- Amber (`#C4862A`) for highlights and selected states — sparingly, never as theme colour
- Never use `bg-white`, `text-black`, `text-gray-*`, `bg-blue-*`, or any colour outside the design system palette

**Status badges — use the semantic system exactly:**
- `PENDING` requisition: `bg-[#FDF3DC] text-[#92650A] border-[#F0D080]`

## Local Development Environment

**Docker is used for all backend services — even locally.** Do not attempt to run PostgreSQL, Redis, the API, or the worker process directly on the host machine.

Start the local stack before any development or testing:
```powershell
Set-Location "d:\AI applications\web\V3-RMS"
docker compose up -d postgres redis api worker
```

Verify the API is healthy before proceeding:
```powershell
Invoke-RestMethod http://localhost:4000/api/v1/health
```

**Run migrations inside Docker:**
```powershell
Set-Location "d:\AI applications\web\V3-RMS\backend"
npx prisma migrate dev --name add_inventory_v2
```
This connects to the Dockerised Postgres on host port `5433` (see `backend/.env` for `DATABASE_URL`).

**Run backend tests inside the Docker context** (tests use the Dockerised test database):
```powershell
Set-Location "d:\AI applications\web\V3-RMS\backend"
pnpm test
```

**Run the frontend separately** (Next.js dev server runs on the host, not in Docker):
```powershell
Set-Location "d:\AI applications\web\V3-RMS\frontend"
pnpm dev
```

**After any backend code change**, rebuild and restart the API container:
```powershell
Set-Location "d:\AI applications\web\V3-RMS"
docker compose up -d --build api worker
```

**Check logs** if the API is not responding:
```powershell
docker compose logs -f api
```

**Never run `prisma migrate dev` in production** — only locally against the Docker Postgres.
**Never run `prisma migrate deploy` without a committed migration file** in `backend/prisma/migrations/`.
