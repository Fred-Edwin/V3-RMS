### Step 2: the walk, one role at a time
**One browser, one window, one tab, for the whole session.** Use the chrome-devtools tools: call `list_pages` once, keep that single page, and change roles by signing out and in **in the same page**. **Never open a new tab or page**, never use a second browser tool, and for phone size use `emulate` or `resize_page` on the same page, then restore. Tell the owner once at the start which window to watch.
Role order: **HR Manager, Director, Accountant, Branch Manager (Nyeri Town), Store Manager, a department head, a staff member (at phone size 390 px), System Admin.**
For each role, repeat exactly this loop:
1. **Announce the plan, then stop and wait for the owner to say "go".** In plain words: "I am going to sign in as <role>. I will do these things in this order: 1 ... 2 ... 3 ... What to watch for: ..." Keep it to a short numbered list, with the real screen names from the menu. Cover: the Home (cards and Needs you), the menu, each People flow that role can do (the owner's list in `1-people-decisions.md`: hire, the employee file and its Edit buttons, change pay with a PIN and the Director's review, probation decision and the head's report, exit and undo, Organisation and heads, the person label in pickers, My file for the person including IDs and bank and the photo, My team), what the role **cannot** do (open one blocked page to show the "Not available for your role" screen), and the sign-in screens the first time.
2. **Do the walk slowly** so a person can follow: one action, a short pause (about 2 seconds), the next. Say in one short line what you are doing before each action. No Paper comparison: the owner is the judge. Do not fix anything you see. If a step fails, say so plainly, note it, and carry on if you can.
3. **Stop at the end of the role and ask: "What should be corrected for <role>?"** Wait for the owner's reply (it can be several lines, including things the owner saw that you did not). Write each point into `docs/features/workforce/final-pass/1-people-walk-feedback.md` **in the owner's own words**, as a table: `# | Role | Where (screen) | What the owner said | Your note (what you saw, or "not seen by me") | Fix or defer (leave blank)`. Read the new rows back in two lines so the owner can confirm. Commit the file after each role.
4. Only when the owner says "next", start the next role. Never move on by yourself.

### Rules
- Plain words with the owner. Edit and Write tools only; a live task list; no subagents; no code or Paper changes in this session except the seed (Step 1).
- Do not ask the owner anything about the code. Ask only "go", "is the data realistic", and "what should be corrected".
- If the session grows long, finish the current role, write everything into the feedback file, commit, and tell the owner: "Clear the context. The feedback file and this brief are all the next session needs; it will continue with <next role>." The feedback file is the memory.

### Final message (after the last role)
(1) A table of the owner's feedback by role (counts) and the ten most important points in one line each, (2) a 5-line recap of what was walked and what was not seen, (3) the lane state (servers stopped, switch off). **Do not draft the next session's prompt.** Stop for the owner.
