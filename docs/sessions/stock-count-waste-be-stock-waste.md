## Build order (one commit per step; gates before each commit)
**1. `waste/log/` (W1, W2) and `waste/_shared/waste-view.ts`.** W1: `often` = this caller's most logged items in the last 60 days (up to 6), `items` = live items of the hub matching the search (retired items never); `unitCost` = the item's current cost, only with `catalog.see_costs`; `onHand` only with `restock.read`. W2: `requireHubActor`; the Central Store location (`locationRepository.findCentralStore()`, not `resolveWasteScope`); one `WasteBatch` per `idempotencyKey` (same key returns the same entries with 200 `replayed: true`; the unique index decides a race); in **one `$transaction`**: one `WasteLog` per entry (`unitCost` = the item's current cost now, `batch_id`, the shared note) and one WASTE ledger row each through `postStockMovement` (`links: { wasteLogId }`, positive quantity in, the door stores it negative); `ITEM_RETIRED`; return `wentNegative` and `totalValueKes` only to those who may see them. Every response goes through `waste-view.ts`.
**2. `waste/reverse/` (W4).** `waste.reverse_any`, or `waste.reverse_own` for an entry the caller logged on the **same Nairobi day**; the service rule decides, with `NOT_YOUR_ENTRY`, `REVERSAL_WINDOW_PASSED`, `ALREADY_REVERSED`. One transaction: lock the log; find its WASTE ledger row; post the reversal through the door (`reversesTransactionId`, same positive quantity; the door flips the sign: stock goes back up); stamp `reversed_at/by`, `reversal_reason`, `reversal_note`. No PIN. Idempotent in effect (a repeat is `ALREADY_REVERSED`).
**3. `waste/entries/` (W3).** Period `today` (the Nairobi day), `7d`, `reversed` (reversed in the last 7 days); `scope=mine` is honoured for everyone, and a caller **without `stock.read`** (the Attendant: they hold `waste.read` but none of the desktop reads) gets **their own entries only, whatever `scope` says**: decide it with that capability test (`actorCan(actor, 'stock.read')` false ⇒ own only), never a role name. KPI cells (Today KES · entries; Last 7 days; Most wasted · the item with the most value in 7 days and its commonest reason "mostly expired"; Reversed 7 days with "Both by the Attendant, same day"/"by …" text built from the data): a reversed entry's value counts for nothing. `bannerText` for the Attendant ("2 items logged at 14:20. You can reverse your own entries today."). Search matches item name and logger. Numbered pager (25/50/100, default 50) and chips counts. Newest first.
**4. `stock/history/` (S3, S4, S5), `stock/_shared/movement-reference.ts`.** The ledger summary, per item for `[from, to]` in Nairobi days (default last 30 days ending today; a future date is `DATE_IN_FUTURE`, `to < from` is `RANGE_INVALID`):
- `opening` = Σ quantity of every ledger row of the item at the Central Store **before** the start of `from`; `closing` = Σ of every row up to the end of `to`.
- By type, signed sums inside the period: `in` = `RECEIVE` + `PREP_PRODUCE` + `DISPATCH_IN`; `sentOut` = `DISPATCH_OUT`; `prepUse` = `PREP_CONSUME`; `waste` = `WASTE`; `adjusted` = `ADJUSTMENT`. Reversal rows are the same type with the opposite sign, so they net inside their own column (a reversed waste entry shows 0 in Waste). **Each row adds up by construction:** opening + in + sentOut + prepUse + waste + adjusted = closing. Test it on a seeded ledger.
- **Money (KES):** every movement is valued at the **ledger row's own `unit_cost`** (the cost in force when it happened); `closingValueKes` per item = Σ quantity × unit cost over rows up to `to`; the KPI strip is Opening value, In, Out (sentOut + prepUse + waste), Closing, with the adjusted amount in the closing caption, so "510,200 + 214,600 − 239,000 − 3,400 = 482,400" holds. All items (S2) values stock at the **current cost** (latest-price costing, `decisions.md`); the two can differ and the README says why.
- Rows: items that have a ledger row or a non-zero opening in the period; filters search (item name, or a reference), `sectionId` (through `count-reads.sectionNamesByItem` / the section tables via counting's read function only), chips `all` / `adjustments` (item has an ADJUSTMENT in the period) / `waste` / `negative` (closing < 0), counts in `chips`. Numbered pager. `note` = "made in Prep" when the item is PREPPED and was produced in the period.
- **References** (search and the card): `ADJ-nnnn` is the ledger row's `reference`; a count adjustment's source is `CNT-…` (through `count_line_id`); `GRN-…` through the delivery line; `PREP-…` through the prep run; **dispatch has no persistent number**: use the dispatch's `sequenceLabel` where Paper draws `DSP-nnnn` (needs-doc N11). `movement-reference.ts` is the one function that turns a ledger row into its reference text.
- S4: the same query as S3, CSV, every row, at most 10,000 (413 `EXPORT_TOO_LARGE`); register `/ledger/export` before `/ledger/:itemId`.
- S5: one item, `show=byDay` (rows per day with a movement, newest first: the 5 most recent, and one collapsed "earlier period" row for the rest, N12) or `entries` (every entry unpaged), chips `daysWithMovement` / `adjustmentsOnly`; `strip` = the period totals; `lastCounted` through `count-reads.lastCountedByItem`; reversed entries carry `reversed: true`.
