# Code session: Purchasing and Receiving, mock-data front-end (Session 1 of 2)

Paste this whole file as the first message of a new agent session. It is a **code lane** (front-end, plus one small back-end change to the permissions table). Run it in lane 1 (or a free lane). Session 2 runs in the same lane **after** this one is merged: [purchasing-mock-session-2.md](purchasing-mock-session-2.md).

## What we are doing and why
The Purchasing and Receiving flow is the part of Inventory the client sees first, and the client has **not approved** it yet (not the flow, not who does what). So we do **not** build the back-end yet. We build the **front-end to the approved Paper design on mock data**, the owner demos it to the client and to each role, feedback changes the screens, and only then do we build the back-end and migrations and remove the mock. The mock runs in the live app (nothing in Inventory is in production use yet).

The decisions are written down: `docs/features/inventory/decisions.md`, section "One screen set, mock first (owner decisions, 4 Oct 2026)". Read it first. In short:
- **One screen set.** Every screen is built once. Every desktop role (Store Manager, Accountant, Director, Branch Manager, System Admin) gets a **Central Store** group in its sidebar and can open every screen. Write buttons show only for the role whose job it is; for everyone else they are **hidden**, not greyed. Read-only variants are not drawn and not needed.
- **Access is one table** (`backend/src/modules/inventory/_shared/central-store-access.ts`). Never a new `requireRole(...)` list.
- **Purchasing roles:** Store Manager and Store Attendant raise orders (the Attendant sends an order *request*; the Store Manager approves with a PIN). The **Accountant does not raise orders**; the Accountant records deposits, invoices and payments. Branch Manager and Director are **read-only**. System Admin reads and writes everything and signs with their own PIN. The Attendant follows the approved phone design only. The client has not approved these mappings: the demo exists to test them, so changing one must be a one-row edit in the table.

3. **Mock layer** in `frontend/features/inventory/purchasing/`:
   - `services/purchasing-service.ts`: the one interface the screens use (the contract's operations). Screens import only this.
   - `mock/`: a **mock engine** implementing the rules from Stage A as pure, tested functions behind that interface, plus fixtures and scenarios.    - **Data:** items and suppliers come **read-only from the real catalog and supplier data** through the existing services (the owner gathered the real data). Orders, deliveries, invoices, deposits and payments are mock and never written anywhere but the browser. First check that the real catalog is available where the demo will run; if it is not, say so and ask. Add the realistic touches: Kenyan suppliers and units, KES amounts, supplier item names and codes on the LPO.
   - **Scenarios** the demo can jump to: an order awaiting approval; an approved order ready to send; a sent order with a deposit; a part-delivered order; a delivery with a price change; an invoice higher than delivery (disputed); an overdue order to pay; an order paid by cheque; a closed purchase file. Build the ones Session 1 screens need now and register the rest as Session 2 completes the screens.
   - **PIN:** the mock accepts the demo PIN `1234` and rejects anything else with the contract's error, so the wrong-PIN state can be demoed.
   - **Contract tests:** one test suite per operation that runs against the service interface, so it can be pointed at the real back-end later. Run it against the mock now.
4. **Demo shell:** a **"Demo data" banner** on every mock screen, and a **demo bar** visible **only to the System Admin** (role switcher: Store Manager, Store Attendant, Accountant, Director, Branch Manager, System Admin; scenario picker; reset).
